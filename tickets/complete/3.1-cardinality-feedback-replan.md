# Re-plan cached statements on a consequential size shift

Fourth of the `cardinality-feedback-*` chain (implementation commit: `ticket(implement): cardinality-feedback-replan`). A **shift** — an observed table size at least `shiftFactor` (10×) from the overlay's baseline — now re-plans prepared statements whose plan reads that table.

## What landed

- `Database.noteCardinalityShift(key)` is the overlay manager's `onShift`; it walks live statements and calls `Statement._noteCardinalityShift(key)` on each.
- Each `Statement.compile()` keeps the overlay keys of every `table` dependency (view and lens bodies share the statement's dependency tracker, so base tables under views are included). A shift on one of them only *marks* the cached plan; `dropPlanOnShift()` at the start of the next `_iterateRowsRawInternal` drops it through `invalidatePlan()` when the cooldown allows.
- `FeedbackReplanState` (in `core/database-cardinality-feedback.ts`): first feedback re-plan immediate, re-plan `k+1` waits `replanCooldown × 2^min(k−1, 6)` execution starts since re-plan `k`; early marks stay pending. Any plan drop (schema change, rebind, batch advance) clears the mark — a deliberate deviation from "a successful compile clears it", argued in the implement handoff and accepted here: a mark can only exist on a live plan, and clearing on drop avoids counting a redundant feedback re-plan after a schema change.
- Tuning knob `cardinalityFeedback.replanCooldown` (default 8). Doc §3.6, §3.9, status line and key-files table updated.

## Review findings

- **Read the diff first, then the handoff.** Checked every changed file plus the surrounding paths it interacts with: `compile()`, `invalidatePlan()`, `dropStalePlanOnBind()`, `nextStatement()`, `tryRouteConcurrent()` / `_iterateConcurrent()`, `all()`'s early `getColumnNames()`, the manager's `record()` / `onShift` / publication error handling, statement registration (`statements.add` sites, `_statementFinalized`), and `storedBodyContext`.
- **Correctness — no defects found.**
  - Mark lifecycle: a mark requires `this.plan`, and every drop goes through `invalidatePlan()` → `onPlanDropped()`, so no stale mark can outlive the plan it was set on. A bind-triggered drop inside `_iterateRowsRawInternal` happens before `dropPlanOnShift`, so it is not miscounted as a feedback re-plan.
  - Committed-read routing: `_isConcurrentReadEligible` checks autocommit state, side-effecting nodes, table-valued function calls and each table's module flag — all invariant under a re-plan of the same AST, so the re-plan after routing cannot invalidate the routing decision.
  - `all()` captures column names from the pre-re-plan plan; the re-plan is of the same AST, so names and count match. `columnDefCache` is cleared by `invalidatePlan()` and recomputed for the representation check.
  - `onShift` runs inside `_publishCardinalityObservations`'s try/catch, so a throw there is logged, never fails a statement.
  - Pacing arithmetic matches the doc and the knob's docstring (`[1, 8, 16, …, 512, 512]`).
  - Table dependencies are always recorded with `schemaName` (`schema-resolution.ts`), the same fields the manager keys on.
- **DRY — fixed.** The overlay key format was spelled twice (manager's private `tableKey` and the statement's `tableDependencyKeys`), and those two strings must match for a shift to reach a plan. Extracted `overlayTableKey(schemaName, tableName)` exported from `database-cardinality-feedback.ts`; both sides now use it. The statement side skips a `table` dependency with no `schemaName` (never produced today) instead of keying it as `undefined.<table>`.
- **Tripwire — parked at the site.** One `FeedbackReplanState` per `Statement` is shared by all members of a multi-statement batch, so one member's feedback re-plan delays the next member's. NOTE added on the `feedbackReplan` field in `statement.ts`.
- **Conditional, already documented — no action.** O(live statements) walk per shift is stated in doc §3.8; turning `cardinality_feedback` off leaves cached plans as-is until their next recompile (doc §3.7), and a pending mark would just cause one extra catalog-only re-plan — harmless.

No tests added — the DRY fix is guarded by the end-to-end test (a key mismatch would fail it).
