## What landed

Implemented in `ticket(implement): collation-checks-resolve-the-chosen-index-like-the-rest-of-the-planner`.

Both collation checks in `rule-select-access-path.ts` — the seek arms' cover analysis (`classifyCollationCover` via `indexColumnCollationLookup`) and the ordering guard (`orderingClaimSurvivesCollation`) — used their own exact-name index lookup and fell back in opposite directions on a miss. Both now go through `resolveIndexKeyCollations`, which resolves via `resolveIndexDescriptor` (module descriptor, then primary key, then case-insensitive schema match). A module descriptor's `keyColumns[].collation` is authoritative; the engine's own primary-key descriptor reads each column's declared collation (the store leaves `primaryKeyDefinition[].collation` stale — see `backlog/bug-store-primary-key-definition-keeps-pre-rewrite-collation`). An unknown collation (unresolvable index, or a column the index does not hold) classifies a BINARY equality as `COARSER_SAFE` (seek + re-check) and everything else as `MISMATCH_UNSAFE` (decline to scan; ordering claim does not replace a Sort).

Behaviour changes: aliased modules with no descriptor get a re-check over BINARY equality seeks and lose collated-equality and range seeks; the duplicate-index-name round-trip test now returns the correct single row because the predicate is re-checked above the seek (pin updated; the other pinned damage is unchanged).

## Review findings

- **Ordering guard checked the wrong index for a plan that names no seek index (fixed).** The implement pass resolved `orderingIndexName ?? indexName`; when both are absent it classified every bearing constraint as unknown collation, so a module claiming primary-key order with a handled BINARY range over a BINARY key kept a needless Sort. Such a plan is built by `selectPhysicalNodeLegacy`, which walks the primary key (`orderingIndexName ?? primary`) — also when `indexName` is set without `seekColumnIndexes`, a pre-existing divergence the old code shared. Added `orderingClaimIndexName` (ordering index, else the seek index on the index-aware path, else `_primary_`) and `usesIndexAwarePath`, which the leaf dispatch now uses too, so the guard and the leaf builder cannot disagree on which path runs. `resolveIndexKeyCollations` and `indexColumnCollationLookup` now take a required `indexName` (the seek arms pass their `idxStrName`). Docs bullet in `docs/optimizer-retrieve.md` updated. No new test: the defect cost only a redundant Sort, and no in-tree module produces that plan shape.
- **Correctness of the unknown-collation rule:** checked by reading `classifyConstraintCover` against each arm (eq, IN multi-seek, range, prefix-range, OR range) and against `rule-key-set-seek`, which still passes a resolved string and declines unresolved descriptors itself. Sound: only a BINARY equality is a superset under every collation.
- **Primary-key behaviour unchanged:** the engine primary-key descriptor reads column collations as before; a module-supplied `role: 'primary'` descriptor is authoritative by design (documented in `docs/module-authoring.md`). Legacy seek arms still use `primaryKeyCollationLookup`; duplication with the primary-key branch of `resolveIndexKeyCollations` is small and both go away together with the store staleness fix — noted on the backlog ticket rather than as a code NOTE.
- **Duplicate-name pin rewrite:** acceptable. The new assertion still pins observable behaviour, and its comment says the re-check rescues only an over-fetching seek, so a future reject/rename decision still flips visible assertions (entry count, `index_info`, `DROP INDEX`).
- **Tests:** the four added tests (which the implement handoff reports all failed before the fix; not re-run at the parent in review) pin distinct contracts (case-insensitive route for ordering and for seeks; descriptor route; no-descriptor rule). None cut. Not added: the guard's unresolved-index range arm and "column not in resolved index" seek arm — both are one-line branches of `classifyConstraintCover` already exercised by the no-descriptor test's NOCASE case.
- **Type safety / error handling / resource cleanup:** no `any`; `indexName` parameters made non-optional; no new failure paths. Unresolved indexes still warn once in `buildIndexAccessPath`.
- **Docs:** `docs/module-authoring.md` ("Naming the chosen index") and `docs/optimizer-retrieve.md` read and accurate after the fix above.
