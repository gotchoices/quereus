# Cardinality feedback: consume rows per key and re-plan on a shift

Second half of the rows-per-key slice (design: `docs/progressive-optimizer.md` §3). Landed in `ticket(implement): cardinality-feedback-rows-per-key`, reviewed here.

## What landed

- **The seam** — `plannedRowsPerKey(table, columns, sources)` in `planner/stats/table-cardinality.ts`: catalog statistics covering every column of the set leave the module's estimate standing (`undefined`); otherwise the overlay's running mean, rounded and floored at one row; otherwise `undefined`. `RowCountSources` now also carries `observedRowsPerKey`, implemented by `CardinalityFeedbackManager` and forwarded by `databaseRowCountSources`.
- **`IndexSeekNode`** snapshots that reader once at construction (for a seek `equalitySeekKeyColumns` accepts, through the source's schema manager) as `plannedRowsPerKey`, and relays it as `estimatedRows` in place of the module's number. The module's own `filterInfo.indexInfoOutput.estimatedRows` is untouched.
- **The index-nested-loop candidate** prices `rowsPerSeek` from the rebuilt seek's snapshot, falling back to the module's `rows`; the module-currency admission gate keeps reading the module's numbers.
- **Shift detection** in `recordRowsPerKey`: a folded mean `shiftFactor` away from the set's baseline resets the baseline, counts a shift and reports under the table's key, so the existing statement marking and cooldown apply unchanged.
- **Emit-time baseline** (`rowsPerKeySpecOf` in `runtime/emit/scan.ts`) is the plan's snapshot when it had one, else the module's estimate, so a plan priced from the mean does not shift on agreeing with it. `columnSetKey` in `runtime/cardinality-observations.ts` is the one spelling of a column set's key.
- **Docs**: `progressive-optimizer.md` §3 (motivating case re-measured, §3.1 to §3.7, §5, §6), `optimizer-costing.md`, `optimizer-joins.md`, `usage.md`, and the backlog ticket `feat-cardinality-feedback-beyond-table-size`.

## Review findings

Read the implement diff first (`ticket(implement): cardinality-feedback-rows-per-key`), then the whole of `database-cardinality-feedback.ts`, `table-cardinality.ts`, the seek node, the index-nested-loop candidate, the scan emitter's observation path, `equalitySeekKeyColumns`, both shipped modules' statistics-coverage rules, and every touched doc.

**Checked and sound**

- **Coverage rule agreement** (the handoff's first review focus): `catalogCoversColumns` applies the same three conditions as the memory module's `equalityTupleSelectivity` and the store module's arm estimate (`rowCount <= 0` reads as no statistics, per-column lookup by lowercase current name, one uncovered column falls back wholesale). The override and the module's own estimate therefore agree on when statistics cover a seek.
- **Multi-key seeks** (`col in (1, 2, 3)`): the module's estimate counts keys times rows per key, while the override is rows for one key. Not a defect: `equalitySeekKeyColumns` admits only plan `eqSeek`, and `IN` lists and runtime sets are plan `multiSeek`, so they never take the override. Whole-primary-key seeks are excluded too because the primary-key pseudo-descriptor carries `unique: true`.
- **Clones and null paths**: `withChildren` and `withProvenance` go through the constructor and re-derive the snapshot in the same synchronous compile; a hand-built node without a schema manager has none; the index-nested-loop rule declines before touching `seek.plannedRowsPerKey` when no seek was rebuilt.
- **Shift semantics**: a per-key shift and a count shift from one execution call `onShift` twice with the same key, and statement marking is idempotent. Eviction then re-creation of a set carries the plan's snapshot as baseline, so a plan priced from the mean does not shift spuriously (by inspection, as the handoff said).
- **Docs**: every touched doc reflects the landed behaviour. `module-authoring.md` says a module's `rows` is "an estimate the engine costs with and nothing more", which does not contradict the engine substituting an observation for its own consumers; left as is.

**Minor, fixed in this pass**

- `plannedRowCount` took the full `RowCountSources`, which forced the manager's `plannedBefore` to pass a stub `observedRowsPerKey` that always answered `undefined`. Narrowed the parameter to `RankedRowCountSources` (the two members it reads) and removed the stub.

**Tripwires**

- Recording a column set the catalog's statistics cover: `plannedRowsPerKey` never consults such an entry under that schema object (an `ANALYZE` swaps the object before coverage can change), so under a stale catalog its first record can shift once and re-plan statements that land the same plan. Parked as a `NOTE:` in `recordRowsPerKey`; the handoff's "catalog-wins is a first rule" `NOTE:` on `plannedRowsPerKey` already carries the revisit condition for the precedence itself.
- The handoff's concern that LevelDB-backed benchmarks were not gated needs no tripwire: `docs/architecture.md` says `store-leveldb` rows are informational and never gated, so a re-planned seek there cannot fail `bench:gate`.

**Major**: none. No class-level invariant is missing: the one definition of "a qualifying seek" is shared by the observer and both planner readers, and the one spelling of a column-set key is shared by the spec and the manager.

**Tests**: all kept. The record-policy test pins the shift rule at the lowest layer; the precedence test pins catalog coverage, rounding and partial coverage against a hand-built sources object (a pure reader over an interface, so that is the right layer); the prepared-statement test covers the end-to-end re-plan. No test added: no defect was found, and the plain-seek relay of the override is a single `??` with no branching worth a test.
