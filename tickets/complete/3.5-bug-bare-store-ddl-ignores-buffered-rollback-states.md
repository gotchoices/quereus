# Bare store: non-committing DDL vs. the states a rollback could restore

## What changed

Commit: `ticket(implement): bug-bare-store-ddl-ignores-buffered-rollback-states`.

**Refusal.** Without the wrapper, `create unique index`, `add constraint … unique` and a `set not null` that sees no NULL judge the committed rows and the rows at each open savepoint, after judging the visible rows. A violation only in a restorable state refuses with `BUSY` ("Commit the pending writes first, then retry."). A violation the transaction can see keeps `CONSTRAINT`. When nothing is buffered for the table, no extra scan runs.

**Arms that flush are exempt.** `set data type` conversion and the UNIQUE re-validation of `alter column` use `judgeRollbackStatesBeforeFlush`, which judges only a wrapper's states. Their flush makes the writes durable and ends the savepoints, so nothing is left to restore.

**Index population.** `populateIndexStore` writes physical entries for committed rows only and queues the ops the transaction's buffered writes owe the new index through the coordinator, each right after its data op so it sits before any later savepoint (`TransactionCoordinator.queueDerivedOps`). Commit, rollback and rollback-to each leave the index as if it had existed when the transaction began. Plain `create index` and the hidden store behind `add constraint … unique` share this path. A failed `create index` discards its queued ops before teardown (`discardQueuedIndexOps`).

**`set not null` with a usable DEFAULT and a NULL only in a restorable state takes the committing backfill rather than refusing.** The backfill's flush ends the states holding the NULL, so it cannot come back. A statement that used to stay inside the transaction now commits it.

## Usage

```sql
-- committed rows: (1,'a'), (2,'a')
begin;
delete from t where id = 2;
create unique index ux on t (v);  -- BUSY: the deleted row would come back as a duplicate
commit;
create unique index ux on t (v);  -- succeeds

-- committed rows: (1,'a'), (2,'b')
begin;
delete from t where id = 2;
create unique index ux on t (v);  -- accepted, row 2 breaks no rule
rollback;                         -- row 2 is back and indexed
insert into t values (3, 'b');    -- CONSTRAINT
```

## Review findings

No source defect was found in the implementation. The review changed two docs and filed one ticket for a neighbouring defect.

**Fixed in this pass (docs only).**

- `docs/module-authoring.md` still named `StoreModule.buildIndexEntries` as the site documenting that a stale index entry is harmless. That comment was removed by this change, and the claim does not hold for a row the module's own buffer overwrote. It now points at `populateIndexStore` and says why. I confirmed `produceIndexEntries` in `store-table-scan.ts` only dedupes for a multi-seek, so a second entry would surface twice from a range scan.
- `docs/memory-table.md` said the store's index is written outside the coordinator. That is now true only of the committed rows' entries, and the text says so.

**Filed.** `bug-add-check-or-foreign-key-ignores-rollback-states` in `backlog/`. The handoff listed this as unchecked. Run on the memory backend and on the bare store, both accepted the statement and restored the violating row on rollback. With CHECK, `select * from t where v <= 0` then omits that row, because the optimizer trusts the constraint. It lives at the engine's shared CHECK scan and the FOREIGN KEY validator, not at this ticket's sites, and it needs design because that scan cannot read a module's rollback states.

**Checked by running, with a throwaway randomized spec (deleted afterwards).** Random inserts, updates (including primary key changes), deletes, savepoints, releases and rollback-tos, with index and constraint DDL mixed in (plain, multi-column, DESC, partial, unique, `add constraint`), ending in commit or rollback. After each run, every physical index store was compared byte-for-byte with a fresh build over the final rows, and the surviving unique rules were checked over those rows.

- In-memory provider: 400 seeds, 447 DDL statements accepted, 20 `BUSY` refusals, 0 failures.
- Real LevelDB through the bare path: 60 seeds, 68 DDL statements accepted, 2 `BUSY` refusals, 0 failures. This closes the handoff's LevelDB gap. IndexedDB remains unrun.
- A `create unique index` that takes over a plain UNIQUE's hidden index, with buffered writes: it flushes, and the index matches a fresh build.

**Other handoff items.**

- The "contrived corner" (a UNIQUE whose implicit index name is held by an explicit index, skipping both the flush and the rollback-state judgement) could not be reached. The engine refused it when the constraint came first, when the index came first, and for an unnamed UNIQUE with an index named `_uc_v`. A route through renames was not run. The comment in `store-module-alter-column.ts` saying this path always reaches a flush stands, on that evidence.
- `iterateEffective` no longer being a generator: all four call sites iterate it immediately, confirmed by reading them, so the earlier read of the pending view changes nothing.
- The two removed tests accepted exactly what this ticket makes a refusal. Removal is correct, and the same shapes are asserted as `BUSY` in the new spec.
- The range-scan tests in the new spec do exercise the index: `query_plan` shows `INDEX RANGE t USING ix` for that query shape.

**Read and found correct, no test added.** `rewriteLog` savepoint repositioning when several savepoints share a position; `queueDerivedOps` when a key is written repeatedly, and when a write's old and new index keys are equal (log order leaves the put winning); `discardOpsFor` ordering against teardown; a failed build having queued nothing, because queuing is the last population step; the wrapper leg, whose `createIndex` behaviour is unchanged since the store holds nothing buffered there; two `create index` statements in one transaction filtering on the data store only.

**Tripwires and decisions left as they are.**

- Scan cost of S + 3 full scans is parked on the existing `NOTE:` at `bufferedRollbackScans`.
- The PK re-key's committed-rows `BUSY` probe can refuse a statement that is safe in bare mode. The doc comment on `validateRekeyedPrimaryKey` already records this as deliberate, so it was not re-filed.
- `set not null` taking the committing backfill: kept. It matches the rule the prereq set and the reasoning holds, but it is a behaviour a human may want to weigh, see above.

**Tests.** None added or cut. Each of the 26 tests in the new spec pins a refusal status, a restored-state result or a failure unwind. The implementer's mutation checks (removing the discard, appending derived ops at the log tail) were not repeated.
