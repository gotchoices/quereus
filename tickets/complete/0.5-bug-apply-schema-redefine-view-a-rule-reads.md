Reported in GitHub issue #39. The reporter's real schema has `TradingVariable`'s CHECK reading the view `TallyClosed`.

## What changed

**The exception.** A forward `DROP` passes the expression guard when the plan creates the same object again under the same name, meaning the name is in `viewsToDrop` and `viewsToCreate`, or in `tablesToDrop` and `tablesToCreate`. Removing a view while a CHECK reaches it stays refused, directly or mid-chain, and so does a hinted rename.

**Re-validation.** After the last step, every CHECK reaching a recreated object, in any schema, runs `rejectCheckViolatedByExistingRows`. A failure takes the failed-step path. The error reads `apply schema 'main': CHECK constraint 'pc' on table 'P' reads recreated 'main.v1' through view 'v2' and fails: ...`, with the scan's error as `cause`.

**Assertions.** One that reaches a recreated object through views or maintained tables is now dropped first and recreated last.

## Where this departs from the ticket

Please check these first, since the ticket did not ask for them.

1. **Prepared statements needed a fix the ticket did not list.** A statement prepared before the apply kept enforcing the old view: `insert` of 11 failed where the new view allows it. By-hand redefinition did not have this problem, because `ADD CONSTRAINT` fires `table_modified` on the table, so the ticket's claim that the apply matches a user redefinition was false without this. Reading a view recorded no dependency on it, and the statement listener ignored `view_added` and `view_removed`. Reads now record a new `view_read` type, which a drop or create invalidates. It is a separate type because `test/plan/view-dependency-invalidation.spec.ts` deliberately pins that a tag change does not invalidate a read plan; those tests pass unedited. This also changes plain DDL: any prepared read or write over a view now recompiles after a drop and create of that view.

2. **The assertion widening counts recreated objects only, not every dropped object as the ticket worded it.** Counting a table that is going away would drop the assertion first, destroy the rows in `DROP TABLE`, and then fail at the recreate as partially migrated. Today that is refused with the rows intact. This matches the ticket's stated rule ("otherwise the guard stays on"). An assertion that directly names a table going away keeps its existing behaviour, which does have that data-loss shape. I did not touch it.

3. **The walk covers catalog bodies as well as the declared ones the ticket named.** The catalog's are what the guard follows when the drop runs: a maintained table the plan re-attaches off the view is refused without them. The declared ones are still needed for a maintained table renamed and moved in the same plan. Each arm has a test that fails without it.

4. **The re-validation scans a CHECK that is already declared, against the caution on `validateChecksOverExistingRows`.** The ticket's design does this, and no record is swapped out. My reasoning is that folding needs the whole `not (...)` proved false, and a conjunct reading a subquery is never lifted as a fact. This is reasoned from `check-extraction.ts` and the contradiction rule, plus section 15 of the logic file, where a lifted sibling conjunct (`u > 0 and ...`) still finds the violating row on both backends. It is the claim I would most like checked.

## Known gaps

- **A view whose CHECK also reads a NOT NULL mutation-context variable cannot be redefined.** Run on memory. The scan has no context to supply, so it refuses with `ADD CONSTRAINT`'s wording ("cannot add a CHECK ... with ALTER TABLE"), which reads oddly here. The same is true by hand and it was already refused before this change. Documented as a limit.
- **Rows that already broke the CHECK under the old view fail the apply.** Run on memory: a table the view reads changed after the row was stored, and even a redefinition that leaves the sum alone is refused. A CHECK over a subquery is only enforced when its own table is written, so this state is reachable. It matches `ADD CONSTRAINT`, and the docs say so, but the failure may read as the new view's fault.
- **A view replaced by a materialized view of the same name stays refused.** Run on memory. The ticket's rule is per bucket, so I kept it. Listed in the docs under the rule itself.
- **A failing CHECK after a module move reads as partially migrated.** The `DROP TABLE` of the move is marked irreversible. Read from the code and not run; the spec covers only the success path.
- **Store coverage is the logic file only.** The spec cases, including the module move, ran on memory. `mem2` in that test is a second memory module.
- **Object keys in the new error are lowercase** (`'main.v1'`), because the scope holds keys rather than catalog spellings.

## Review findings

Read `ticket(implement): bug-apply-schema-redefine-view-a-rule-reads` before the handoff, then ran throwaway specs on the memory module (deleted afterwards). `yarn lint` and `yarn test` exit 0 after the review edits. `yarn test:store` was not re-run: the only source change in review is a failure-path refactor with no module-specific behaviour, and the implement run passed on store.

**Checked, and held:**

- Scan folding, the implementer's main question. A declared CHECK reading a subquery does not fold the scan. A row that violates the new view was found for `in (select ...)`, `exists`, a lifted sibling conjunct plus `in`, `or`, `between`, `=` and `case`. `check-extraction.ts` agrees: its recognizers need a column and literal, so a subquery operand mints no fact, and a conjunct's fact only removes that conjunct from the `not (...)`, never the one reading the view. Logical tables, which have no module and would make the scan throw, live only in lens slots and are never in `getAllTables`.
- Prepared statements. Reads and writes recompile across a redefinition: direct, through a chain, with a CHECK through a chain, through a qualified name of different case, and by hand with a different-case drop and create. A prepared read of a dropped view now fails with `Table 'V1' not found` instead of serving the old body. A tag change still keeps a read plan cached (spec already pins it). `view_read` is ignored by the other dependency consumers (`ReportedSizeSnapshot.capture`, `tableDependencyKeys`), which filter on `'table'`.
- Scope lifetime. After a successful or a failed apply, a hand `drop view` is refused again, and a statement prepared before a failed apply keeps enforcing the old view.
- Non-`main` schemas. A CHECK and a view in schema `s`, and an assertion through a chain there, apply. The recreated set's keys include the schema, read from the code; the only same-name case run applied the two schemas separately, so it did not test both in one plan's scope.
- Plan order when the rule changes too. Changing a named CHECK along with the view, adding a CHECK to an existing table over a redefined view, and a new table with such a CHECK all apply, since `ADD CONSTRAINT` and table creates see the new view or are judged afterwards.
- Staged rows. The scan sees a row staged earlier in the transaction and refuses when the new view rejects it.
- Bucket timing. All create and drop buckets are filled before `recreatedObjectReachProbe` runs (`schema-differ.ts`, lines 725 to 816 against 982).
- A throw from `findChecksReachingObjects` sits outside the step `try`, but `runBatchedMigrationLoop` guards unexpected throws and still ends the batch. Left as is.
- Tests. Read as code under review. Each spec case reaches something the logic runner cannot, and the logic sections each pin a stated rule. None cut. None added, because the probes found no defect in this change that a test would pin.
