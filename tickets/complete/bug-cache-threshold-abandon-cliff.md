## What changed

`CacheNode` (runtime: `streamWithCache` in `runtime/cache/shared-cache.ts`) buffers its source on the first pass and replays it on later passes. It used to drop the buffer when it reached `threshold` rows and re-run the source on every later pass. That state (`cacheAbandoned`, both abandon branches, `getCacheMetrics().isAbandoned`) is gone.

- **Runtime (soft guard).** Both build modes (streaming-first and eager) push every row through one helper, `bufferRow`. When the buffer first grows past `threshold`, it logs one line on `quereus:runtime:cache:shared:warn` and keeps buffering. A source that a consumer drains runs at most once per execution, at any size. The helper carries the `NOTE:` that buffers are unbounded, like hash-join builds and CTE materialization. The replay loop carries the `NOTE:` about copying each row on every replay. `CacheStrategy` / `SharedCacheConfig` docs now say that `'spill'` is not yet acted on.
- **Threshold formula.** `CachingAnalysis.getCacheThreshold(node, tuning)` = `thresholdForEstimate(estimatedRows, tuning)` = `max(ceil(E × join.cacheThresholdMultiplier), 1000)`, with no upper cap. The old formula was `min(max(E × 0.1, 1000), 100000)`. All three cache rules and the materialization advisory use it now. The advisory's private `calculateThreshold` (capped at 10k, or 20k for spill) is deleted.
- **Tuning.** `join.maxCacheThreshold` and the whole `cte` block (`cte.maxCacheThreshold`) are removed from `OptimizerTuning` / `DEFAULT_TUNING`. No package outside `packages/quereus` referenced them (checked with grep).
- **Comments.** I updated the stale "pass-through" / "abandon" wording in `cache-node.ts`, `rule-nested-loop-right-cache.ts`, `rule-subquery-decorrelation.ts`, and the `buffered(...)` read-ahead comment in `emit/cache.ts`. I left the `plan.threshold > 50000` read-ahead condition as it was. It now fires when the estimate is above 25,000 rows, and it never fires on a misestimate found at runtime.
- **Docs.** `docs/runtime-caching.md` has a new "Run once, at any size" paragraph under § CacheNode row-cache lifetime. The eager-mode sentence and the IN-set-probe history sentence are corrected.

## Known gaps noted at handoff

- **Early-stopping consumers still re-run the source.** In streaming-first mode, a consumer that stops early (a semi or anti nested-loop `break`, a `limit`) leaves nothing committed, so the next pass re-runs the source. This was already true before and was not changed. It is fine for read-only sources. For a DML source wrapped by `rule-mutating-subquery-cache`, a semi or anti join whose right side is a FROM-position DML would re-fire writes until one outer row drains it. I did not check whether such a plan can actually be built (the DML-bearing subquery paths may never decorrelate into a semi join). If it can, the fix is for that rule to set `eager: true`. It is worth a look.
- **The 50,000-row size gate stays.** The nested-loop rule still refuses to cache a right side estimated above `join.maxRightRowsForCaching` (50,000). That gate is estimate-based and was out of scope. With unbounded buffers elsewhere, refusing to cache now means N full scans of a big table where one buffer would do. That is a separate decision.
- **Warning message.** It reads "estimate was low", which is true by construction: the threshold is a multiple of the estimate, floored at 1000. The 1000-row floor means small estimates warn only past 1,000 rows.
- **`thresholdForEstimate` is public static** on `CachingAnalysis` so the advisory can call it with its reference-graph estimate (it has no node, only `RefStats.estimatedRows`).

## Review findings

I read the diff of `ticket(implement): bug-cache-threshold-abandon-cliff` before the handoff. I checked the runtime, the threshold formula, all four places that create a `CacheNode`, the tuning removal, the docs and the tests.

- **Correctness (runtime).** `bufferRow` warns exactly once: the check `buffer.length === threshold` runs before the push, and every threshold is an integer (`thresholdForEstimate` rounds up with `ceil`; `CacheNode`'s default is 10000). Both build modes commit only after the source drains, and a source that throws still leaves nothing committed (covered by existing tests). I confirmed it end to end against a fresh `dist` build. With 2,500 source rows, the FROM-position `insert … returning` join wrote 2,500 rows once, returned 7,500 join rows, and logged one `quereus:runtime:cache:shared:warn` line at 2,000. No defect found.
- **Handoff gap: an early-stopping consumer re-running writes.** I checked every place that builds a semi or anti join (`rule-subquery-decorrelation`, `rule-semijoin-existence-recovery`, `rule-inner-join-existence-recovery`). Each refuses a right side with side effects, so `rule-mutating-subquery-cache` only ever sees inner, left or cross joins, which drain the right side for every outer row. A `limit` over a DML source keeps draining it already (`docs/sql-select.md`). So this is conditional, not reachable. I recorded it as a `NOTE:` tripwire at the `CacheNode` construction in `rule-mutating-subquery-cache.ts`: if a consumer that stops early ever reaches that rule, build the node with `eager: true`.
- **Tests (fixed).** Both new SQL-level reproductions used 1,500 rows. That beat the old 1,000-row cap, but the new threshold for these plans is 2,000 (default 1,000-row estimate × multiplier 2; I checked with `query_plan`). So neither test grew the buffer past the current threshold, and a cap reintroduced at the threshold would pass them. I raised both to 2,500 rows, which overruns the threshold: § 6b of `01.9-query-expr-dml.sqllogic` now expects counts 7500 and 2500, and the case in `nested-loop-right-cache-scan-count.spec.ts` was renamed. I corrected their comments, which had claimed the 1,000-row threshold.
- **Tests (kept as is).** The `cache.spec.ts` rewrites assert behaviour (all rows delivered, then replayed from an empty source), not internals. Deleting the duplicate IN-subquery test was right: without its override it was the same as another test in that file. The `characteristics.spec.ts` threshold test is weak (it only checks the threshold is a number greater than 0). It predates this change, which only touched its call signature, so I left it.
- **Docs.** `docs/runtime-caching.md` is accurate. `docs/optimizer.md` § Cache Injection still had pseudocode calling the old `calculateThreshold`, so I replaced it with `CachingAnalysis.getCacheThreshold(node, context.tuning)` (fixed). A grep for `maxCacheThreshold`, `cacheAbandoned`, `isAbandoned` and `tuning.cte` across `packages/` and `docs/` finds nothing left.
- **DRY / modularity.** The two copies of the threshold formula (the advisory's private `calculateThreshold` and `getCacheThreshold`) are now one function. Making `thresholdForEstimate` public is reasonable, because the advisory has an estimate but no node. No findings.
- **Performance and resources.** Buffers are now unbounded. The implementer parked that as a `NOTE:` at `bufferRow`, and the per-replay row copy as a `NOTE:` in the replay loop. I agree with both and added nothing. The `plan.threshold > 50000` read-ahead in `emit/cache.ts` now fires for estimates above 25,000 rows instead of above 500,000 rows, so more plans read ahead. Its buffer is capped at 5,000 rows and it does not change results, so this is not a finding.
- **The 50,000-row size gate in the nested-loop rule.** Out of scope, as the handoff says. Above that size the plan scans the right side once per outer row. Whether to cache there is a separate cost decision, and nothing in this change makes it worse. No ticket filed.
- **Type safety and error handling.** `getCacheThreshold` now requires `tuning`, so the type checker caught every call site (lint type-checks the test files too). No exceptions are swallowed. No findings.
