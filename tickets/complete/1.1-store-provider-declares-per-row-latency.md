# Store providers can declare a per-row read latency

Landed in `ticket(implement): store-provider-declares-per-row-latency`. The per-row hint (`expectedRowLatencyMs`, wall-clock ms per row after the first in a sequential iterate) now follows the same path as the first-row hint, end to end:

- `KVStoreProvider.expectedRowLatencyMs?: number` (`kv-store.ts`).
- `resolveExpectedLatencyMs(declared, field = 'expectedLatencyMs')` in `cost-profile.ts`. It is shared by both hints; `field` only names the hint in the warning.
- `StoreModuleBase.expectedRowLatencyMs` is resolved once at construction (`0` when undeclared or unusable).
- `IsolationModule.expectedRowLatencyMs` is a live getter that forwards the underlying module's value (or `0`).
- The LevelDB and IndexedDB provider `NOTE:`s now record that both hints are declined, and why.
- Docs updated: store README ("Backend per-row latency"), the isolation README forwarding paragraph, the `module-capabilities.md` row, `optimizer-costing.md`, and the queued item removed from `progressive-optimizer.md` §5.
- Test: `expected-latency-plan.spec.ts` › "per-row latency reaching the planner". Over an isolated store, declaring 1 ms/row turns a hash join into an index-nested-loop seek plan. This exercises provider → StoreModule → IsolationModule → planner.

Next on this thread: `feat-indexeddb-declares-its-read-latency` (backlog), which measures and declares real numbers.
