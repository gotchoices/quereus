# The planner asks the module how big a table is

## What landed

- **Hook.** Optional `VirtualTableModule.getRowCount?(db, table): ModuleRowCount | undefined` (`{ rows, exact }`, exported from the package root). Contract on its doc comment: answer from memory in constant time or decline, never start I/O; `rows` is what a read issued now would see; `exact` only for a count maintained on every write; a hint only.
- **Seam.** `plannedRowCount(table, sources)` ranks exact module count → observed overlay → approximate module count → catalog (`ANALYZE`) → `undefined`. One `RowCountSources` per `Database` (`databaseRowCountSources`), shared by `CatalogStatsProvider` and `TableReferenceNode` (via `SchemaManager.getRowCountSources()`). `reportedRowCount` treats a throw or malformed answer as a decline (debug-logged).
- **Overlay baseline.** `CardinalityFeedbackManager.record` computes `before` through `plannedRowCount`, so a scan agreeing with an exact module count shifts nothing.
- **Modules.** `StoreModule.getRowCount` reports `getKnownRowCount()` as exact (declines while no count is in memory). `IsolationModule` forwards it only when the underlying has it; the connection's uncommitted overlay rows are not netted in (documented). Memory backend unchanged (`feat-memory-backend-sizes-itself`).
- **Seek FD fix.** A full-primary-key `IndexSeekNode` whose keys reference columns (a correlated seek, the inner side of a nested-loop join) no longer stamps the "at most one row" dependency (`∅ → all columns`). That false claim reached the join and collapsed its key to the empty key, so a materialized view over the join rejected its second row as a duplicate. Store tables reach that plan shape without `ANALYZE` now, which is how `41.3-alter-rename-propagation.sqllogic` exposed it.

Behaviour changes on purpose (release notes): an exact store count outranks a stale `ANALYZE` snapshot; never-analyzed store joins plan like analyzed ones; a full-rebuild-only materialized view over a never-analyzed store table above `materialized_view_rebuild_row_threshold` is now rejected at `create`; `cardinality_feedback = false` does not disable module counts; a cached statement keeps the count it compiled with, and a full scan no longer re-plans it on growth until `replan-when-a-reported-row-count-drifts` lands; bench counter `execution/join-1kx1k@store-mem` re-baselined.

## Review findings

Read the implement diff (`ticket(implement): feat-planner-asks-the-backend-how-big-a-table-is`) before the handoff, then probed with throwaway specs (deleted afterwards).

**Correctness — seek FD fix (the handoff's main ask).** Checked what relied on the false claim. Consumers of "at most one row" are `keysOf`/`isAtMostOneRow` (join key coverage in `key-utils.ts`, ORDER BY pruning, materialized-view keys), `hasSingletonFd` (join greedy commute, async gather) and `characteristics.guaranteesUniqueRows` (no callers). Losing the claim on a correlated seek is fail-closed: join key coverage still comes from the join's retained equi-condition. Probed on the memory backend with large analyzed inner tables, which plan nested loop + correlated seek: primary-key inner, non-primary-key `unique` inner, left join, and seek under a residual filter. All keep the join key `[[0]]`, no node claims at most one row, and materialized views over them hold every row. The other producers of the same claim were checked for the same defect. The Filter covered-key path already excludes correlated bindings (`bindingReferencesOuterTable` in `constraint-extractor.ts`), so the seek fix brings the seek in line with existing policy. A `lateral (… limit 1)` join keeps the right key and ordering, and its materialized view holds 3 rows. No class-level gap found, so no ticket.

**Correctness — measured zero now reaches the store (major, filed as an arm).** Before this change, a never-analyzed store table's request arrived `undefined`, and `sizeRequestFromLiveCount` substituted the live count floored at 1. Now the planner sends the exact live count, so a store table drained to 0 rows arrives as `estimatedRows: 0`. The store honours a supplied 0 verbatim, so costs price at zero. Verified with a plain `StoreModule` over an in-memory provider: after insert + delete, `select * from t where id = 5` plans as `FILTER (id = 5)` over `INDEX SEEK t USING primary`, the wasteful shape of `bug-declined-push-down-is-rebuilt-as-seek-plus-duplicate-filter`. A one-row table plans a bare seek. Results stay correct; the work is wasted. The decision to floor a measured zero for costing is already made in `bug-measured-empty-table-costed-as-thousand-rows` (implement, sequence 3), whose edge-case list said "store's floor untouched". That ticket now carries a store arm, with test and TODO lines and `store-module.ts` added to its files. A never-touched empty store table declines the hook (`getKnownRowCount` is `undefined`), so it is unaffected.

**Correctness — the rest.** `plannedRowCount` order matches §3.3 and the precedence test. Module lookup by `vtabModuleName` is the same route `TableReferenceNode` uses to get its module (`resolveVtabModule` / global scope). `record`'s baseline uses the same seam; observations from an open transaction are held until commit, so the isolation forward's committed-only count cannot fake a shift. `StoreModule.getTable` lower-cases its key, so names match the way the store keys them. No defects.

**Isolation forward vs. contract.** Accepted by plan and documented at the forward, in the inventory and in the isolation README. Left as is.

**Error handling.** Throw and malformed answer → debug log + decline, per the contract ("a failed hint must never fail planning"). Checked by reading only, as the plan specified. Acceptable.

**Performance / resources.** Each `plannedRowCount` adds a module map lookup and an O(1) store lookup. Negligible. The implementer's tripwire `NOTE:` in `record` (an exact module count still takes an overlay least-recently-used slot) is sound; left in place.
