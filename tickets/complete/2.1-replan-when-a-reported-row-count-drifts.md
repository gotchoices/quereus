# Re-plan cached statements when a module-reported row count drifts

## What was built

A prepared statement re-plans when a table size reported by the table's module (`VirtualTableModule.getRowCount`, e.g. the store's running count) moves 10× or more from the size its cached plan was costed with. Before this nothing caught it: overlay shifts come only from complete scans, a seek plan never makes one, and a complete scan of a module-sized table compares against the live count, so it never shifts.

- `ReportedSizeSnapshot` (`core/database-cardinality-feedback.ts`): `capture(db, dependencies)` keeps `{ table, plannedRowCount ?? defaultRowEstimate }` for every `table` dependency whose module implements `getRowCount` (answering or not, via `moduleReportsRowCount` in `planner/stats/table-cardinality.ts`); `drifted(db)` applies the overlay's shift rule (`spread ≥ shiftFactor`, larger side `> minRows`) and skips replaced catalog objects.
- `Statement`: captures right after `optimize` in `compile()`, resets in `invalidatePlan()`, and `dropPlanOnShift()` marks the plan on drift before the shared cooldown (`FeedbackReplanState`) decides.
- Docs: `progressive-optimizer.md` §3.6 (second trigger), §3.7, §3.8 (overhead measurement), §3.9, §5, §6; `store.md` one sentence.
- Test: `cardinality-feedback.spec.ts` › *re-plans when a module-reported size drifts 10x from the one the plan was costed with* — `HashJoin` at 50 reported rows, `Join` + `IndexSeek` after 20,000, and no re-plan at 30,000 (measured against the new snapshot, not the first).

## Review findings

Read the `ticket(implement): replan-when-a-reported-row-count-drifts` diff first, then the handoff.

- **Correctness — checked, no defect.** Capture runs in the same synchronous turn as `optimize`, so the kept sizes are the ones the plan's table references read. Dependencies are a deduplicated set with `schemaName` always set for tables (`schema-resolution.ts`), and names match `findTable`. A fresh or invalidated statement has an empty snapshot, so the pre-compile `drifted` call short-circuits. A replaced catalog object (`ANALYZE`, `ALTER`) fires `table_modified`, which invalidates the plan and clears the snapshot, so the skip in `drifted` is only defence and cannot silently disable detection. The `minRows` floor and the 1000-row unknown default interact as the handoff says: from an unknown, drift fires only at ≥ ~10,009 rows.
- **Unverified branch, checked by hand (no test added):** a module that declines at compile time and starts answering later. A scratch spec (deleted afterwards) showed the statement kept its `HashJoin` at 5,000 reported rows and re-planned to a seek at 20,000. It is a one-line `!== undefined` check, so it does not earn a permanent test.
- **Write targets kept too (handoff gap) — tripwire.** It is conditional (it only matters if bulk-load re-plans ever show up in a profile), so I recorded it as a `NOTE:` in `ReportedSizeSnapshot.capture` instead of filing a ticket.
- **Repeated debug log during a cooldown wait — declined.** It is debug-only, and the check costs the same either way. Not worth exposing `FeedbackReplanState`'s mark.
- **DRY.** `drifted` repeats the overlay's shift comparison (`rowCountSpread` plus a `minRows` test), but the overlay tests `minRows` against `before` and the spread against the baseline, so the two do not share one shape. Left as is.
- **Concurrent committed reads.** `tryRouteConcurrent` checks eligibility on the cached plan before `dropPlanOnShift` may re-plan. The overlay shift trigger has the same ordering, so this is not new. No action.
- **Performance.** I re-read the implementer's microbenchmark (0.27 µs capture, 0.19 µs check, against 3.9 ms per query) and the before/after bench runs with identical work counters. I did not re-run the bench. The two rows it flagged re-measured as noise.
- **Tests.** The added test pins the specified behaviour, which has real branching (drift fires, and the snapshot rebases after a re-plan). Kept. It depends on a never-analyzed `mid` planning as a hash join. I added it to the re-point note in `tickets/fix/5-unknown-size-join-scans-instead-of-seeking.md`, which already lists this spec file among those its fix will change.
- **Docs.** §3.6–3.9, §5, §6 and `store.md` match the code (unknown read as `defaultRowEstimate`, not gated by `cardinality_feedback`, transaction-buffered counts). No other doc needed changes.
- **Validation.** `yarn workspace @quereus/quereus lint` is clean. `yarn test` passes everywhere (quereus 10841 passing, 25 pending; no failures in any workspace). The cardinality-feedback spec passes alone (9). I did not re-run `yarn test:store` in review; the implementer ran it (10833 passing), and my only code change is a comment.
