# Measured zero: reported as 0, priced as one row

## The rule

A row count has two spellings: `undefined` = nobody measured; a number, including `0`, = a measurement. Sites that **relay** a count keep the 0. Sites that turn a count into a **cost** floor a measured 0 at one row, because a zero goes stale on the first insert and a table priced at nothing undercuts every seek (a point query on a table analyzed empty, filled since, `auto_analyze` off, would trade its primary-key seek for a full scan). Documented in `docs/optimizer-costing.md` § Base-table row estimates.

## What landed

- Relays switched `||` → `??`: `rule-select-access-path.ts` `selectPhysicalNode` (`accessPlan.rows ?? 1000`) and `createSeqScan` (`tableRef.estimatedRows ?? 1000`; `seqScanCost(0)` is `SEQ_SCAN_BASE`, so no floor needed).
- Cost sites floor through one helper, `costedRows(rows, unknownDefault)` in `planner/util/row-estimates.ts`: join selection's `sideRows` / `rowsRead` (unknown → 100) and the memory module's table size (unknown → 1000). The store's `sizeRequestFromLiveCount` floors a supplied 0 itself (separate package), keeping the stale-empty-snapshot substitution of the live count. The isolation layer's no-`getBestAccessPlan` fallback floors its cost.
- `query_plan().est_rows` = physical estimate, else logical, else `null` (was `logical || 10`, which showed 10 for every physical access node).
- NOTEs and docs (`optimizer-costing.md`, `progressive-optimizer.md` §3.7, `module-authoring.md`) updated to the rule.
- Tests: `access-plan-request-row-count.spec.ts` — an analyzed-empty table's scan prices like a one-row table and reports 0 (fails before); a stale-empty table still seeks its primary key (guards a bare `??` swap). `store-row-count-to-planner.spec.ts` — a store full scan with `estimatedRows: 0` equals the one-row plan and a PK seek undercuts it (fails before). `key-set-seek.spec.ts` "compound shape" fixture now seeds 2000/1000 rows before `analyze` (it relied on empty tables collapsing to the unknown default).
