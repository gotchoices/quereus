# Observe complete table enumerations at the scan leaf — complete

Second of the `cardinality-feedback-*` chain (design: `docs/progressive-optimizer.md` §3.1, §3.5, §3.8). Code landed in two runs: the first run's code is in the timeout commit (`tess: timed out on cardinality-feedback-scan-observations — added resume note`), docs and re-verification in `ticket(implement): cardinality-feedback-scan-observations`.

## What was built

- **Eligibility at emit time** — `enumeratesWholeTable(plan)` in `runtime/emit/scan.ts`: not an `IndexSeekNode`; no constraints, `limit` or `offset`; access path `fullScan`, or the primary index walked with plan `scan`. Any runtime `FilterInfo` override (`OrdinalSlice`, key-set semi-join) disqualifies the site.
- **Counting** — a generator-local `rowsYielded++` per row; `observe(schema, rows)` runs only after the row loop exhausts naturally (never in `finally`), so early `return()`, abort and error record nothing.
- **Sink** — `runtime/cardinality-observations.ts` `CardinalityObservations`, keyed by `TableSchema` object (last count wins per execution); `RuntimeContext.cardinalityObservations`, fork policy `shared-sink`.
- **Option** `cardinality_feedback` (boolean, default `false`); turning it off clears the overlay. Gate is the sink's presence at run time, so no recompile is needed.
- **Run sites** — `Statement._iterateRowsRawInternal` and `Database._executeSingleStatement` create the sink and publish it in their `finally`, before any implicit-transaction commit/rollback, via `db._publishCardinalityObservations` (warn-logged on failure).
- **Publish** — `CardinalityFeedbackManager.publish`: applies for `readCommitted` executions or when no transaction is open; otherwise discards (interim, until `cardinality-feedback-commit-scoped-publication`).

## Review findings

**Diff read first** (both commits), then the handoff.

- **Correctness — publish ordering vs implicit transactions:** checked every Statement entry point (`run`, `get`, `all`, `iterateRows`, `iterateRowsWithTrace`, concurrent path) and `_execBatchAutocommit` / `_execBatchAsTransaction`: in each, `_finalizeImplicitTransaction` / `_commitTransaction` runs after the run site's `finally`, so a writing statement in autocommit always publishes with the implicit transaction open and is discarded. Probed with a temporary spec: `delete from big`, a prepared `delete`, and `update big …` each observe the full pre-write count and are discarded. This is a real hazard (a published pre-delete count for an emptied table) and only the explicit-`begin` case was tested, via the `db.eval` run site. **Fixed:** added one test, `db.exec('delete from big')` → no entry, which also covers the otherwise untested `_executeSingleStatement` run site; confirmed it fails when the transaction gate in `publish` is disabled. It survives the next ticket (a table changed by its own transaction stays excluded there).
- **Correctness — error path publication** (handoff question): confirmed correct. A statement that throws publishes only scans that completed; with no transaction open those read committed state, and with one open they are discarded.
- **Correctness — two `TableSchema` objects for one table in one execution** (handoff question): none found. `tableNameRemap` is set only by the deferred-constraint queue's hand-built context, which has no sink. Even if it happened, `record()`'s schema-identity check ignores the superseded object, so the object key is strictly safer than a name key.
- **Docs inaccuracy — "internal run sites create no sink":** wrong. Assertion violation queries, foreign-key actions, `ALTER` constraint checks, materialized-view initial fill, `alter-table`'s probe and auto-analyze's `exec('analyze …')` all run through a prepared `Statement` and therefore get a sink. Harmless: the publish-time transaction rule governs them (commit-time assertions and statement actions run with a transaction open and are discarded; anything outside a transaction read committed state). **Fixed** the wording in `docs/progressive-optimizer.md` §3.1 and the `RuntimeContext.cardinalityObservations` doc comment in `runtime/types.ts`.
- **Docs gap — option not in the user-facing options table:** **fixed**, added `cardinality_feedback` to `docs/usage.md` § Available Options.
- **Concurrency — stale publication from a long committed read:** a committed read that starts before a writer's commit and finishes after it publishes the pre-commit count over the fresher state; §3.7 said "the later write wins" without saying it can be the older state. Conditional (estimates only, next full scan corrects it) — **tripwire** recorded in `docs/progressive-optimizer.md` §3.7 with the revisit remedy (tag observations with the commit they read).
- **Performance — feedback-off overhead** (handoff's open caveat, `full-scan-10k` +10–11% against a stale baseline): settled with an interleaved A/B on identical builds, the built `dist/src/runtime/emit/scan.js` with vs without the sink read, increment and observe lines (`node bench/run.mjs --filter full-scan-10k --no-counters`, 5 alternating runs each). Medians: memory `full-scan-10k` 7.90 ms with vs 7.69 ms without (+2.7%, row spread ~7%); `full-scan-10k@store-mem` 12.69 vs 12.71 ms (0%). Within noise — the earlier +10% was machine drift. `cardinality-feedback-on-by-default` measures only the default flip and need not repeat this. Result files and the patched build were removed/restored afterwards.
- **Eligibility arms** (nested-loop re-scan, self-join, secondary index, range seek, override): re-checked by reading `enumeratesWholeTable`, `IndexPlanKind` and both `emitSeqScan` override callers; `kind: 'empty'` and `unresolvedIndex` correctly never qualify. No parallel operator partitions a table scan across forks (only `async-gather`, `eager-prefetch`, `fanout-lookup-join` fork), so `shared-sink` cannot see partial counts as whole tables.
- **Resource cleanup / error handling:** publication is inside each run site's existing `finally` after disconnects, wrapped in try/catch with a warn log; no new resources. Nothing found.
- **Type safety / hygiene:** no `any`; comments state reasons (why unconditional increment, why never in `finally`). `database.ts` is large but this change added ~30 lines to an existing pattern; nothing to extract.
- **Tests:** the implementer's five tests each pin a distinct branch (positive path, early termination, seek exclusion, interim transaction discard, option gate); none restate implementation or mock owned modules — kept. One added (above).
- **Validation:** `yarn lint` (packages/quereus) exit 0; `packages/quereus` `yarn test` 10829 passing, 25 pending, 0 failing; `yarn docs:check` OK (two pre-existing near-cap warnings on unrelated docs). Targeted specs (`cardinality-observations`, `cardinality-feedback`, `fork-contract`) pass.
