# Store providers can declare a per-row read latency

`feat-per-row-latency-cost-for-remote-scans` adds `VirtualTableModule.expectedRowLatencyMs` — wall-clock milliseconds per row a read yields after the first — and prices every join candidate by the rows it actually pulls. This ticket gives the store stack the same path the first-row hint already has (`store-module-latency-hint-wiring`), so a key-value backend behind `StoreModule` can declare it.

## Design — mirror the first-row hint exactly

- `KVStoreProvider.expectedRowLatencyMs?: number` (`common/kv-store.ts`), documented next to `expectedLatencyMs`: wall-clock, not a ratio; per row after the first, for a sequential iterate; omitted means 0; declare only measured numbers.
- Resolution: validate it with the same rule as the first-row value (finite and `>= 0`, else 0 with one warning). Generalize `resolveExpectedLatencyMs` (`common/cost-profile.ts`) to take the field name for its message rather than writing a second copy.
- `StoreModuleBase.expectedRowLatencyMs: number`, resolved once at construction beside `expectedLatencyMs` (`common/store-module-base.ts`).
- `IsolationModule`: a forwarding getter `expectedRowLatencyMs` returning the underlying's value or 0, beside the `expectedLatencyMs` getter — a live getter for the same reason (an out-of-tree module may learn its value at connect time). `isolation-module.ts` is on the oversized list (`debt-oversized-source-files`): add the getter and its doc comment, nothing else.
- No in-tree provider declares a value. Update the NOTEs at the LevelDB provider (`quereus-plugin-leveldb/src/provider.ts`, "no `expectedLatencyMs` either") and the IndexedDB provider to say both hints are declined, and why (unmeasured for LevelDB; for IndexedDB, pending `feat-indexeddb-declares-its-read-latency`).

## Edge cases & interactions

- **Undeclared provider** resolves to 0 — byte-identical plans. Verify: `yarn workspace @quereus/store test` and `yarn test:store` (foreground; both unchanged).
- **Bad declarations** (negative, NaN, Infinity) degrade to 0 with a warning, through the shared resolver. Verify: inspection — the resolver's existing tests cover the rule; do not add a parallel set.
- **Isolation wrapper** forwards the underlying's value; the overlay (an in-memory staging table) contributes nothing. Verify: the test below runs through `createIsolatedStoreModule`.
- **First-row and per-row are independent**: a provider may declare either. Verify: inspection.

## Tests (only this)

In `quereus-store/test/expected-latency-plan.spec.ts`, one case: an isolated store module over an in-memory provider declaring a first-row latency and a per-row latency plans the fixture join with an index-nested-loop where the same provider declaring only the first-row latency plans a hash join (pick sizes from the formulas in `docs/optimizer-joins.md`, after the prerequisite ticket's rewrite; state the arithmetic in a comment). That one case proves the provider → module → wrapper → planner path end to end.
