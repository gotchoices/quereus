# Re-plan cached statements when a module-reported row count drifts

`feat-planner-asks-the-backend-how-big-a-table-is` lets a module's own row count (`VirtualTableModule.getRowCount`) reach `plannedRowCount`, ahead of the observed overlay when the count is exact. That count changes on every write without any event the planner hears, so a prepared statement compiled when a store table held 10 rows keeps its plan as the table grows to a million. The existing feedback re-plan (`docs/progressive-optimizer.md` §3.6) cannot catch it: shifts come only from complete-scan observations, a seek-based plan never produces one, and since the prerequisite ticket the overlay measures a shift against the *current* live count, so even a complete scan reports no shift.

## Design

Pull, not push: there is no notification to subscribe to, and the per-statement check is cheap.

- **Snapshot at compile.** After a successful compile, for each `table` dependency of the plan whose module implements `getRowCount`, keep `{ table: TableSchema, rows: plannedRowCount(table) }` — the count the plan was costed with, read in the same synchronous compile, so it is exactly what the plan's `TableReferenceNode`s saw. Tables whose module has no hook are not snapshotted (overlay shifts and schema changes already cover them).
- **Check at execution start.** Where `Statement.dropPlanOnShift` consults `FeedbackReplanState.onExecutionStart`, first compare each snapshot entry with the current `plannedRowCount(table)`; when `spread(now, then) >= cardinalityFeedback.shiftFactor` **and** `max(now, then) > cardinalityFeedback.minRows`, call `markShift()`. The existing cooldown then decides whether this execution re-plans. An unknown on either side reads as `tuning.defaultRowEstimate` (what the plan used, or will use); a table whose current catalog object is no longer the snapshot's object is skipped — its schema change already invalidates the plan.
- **Placement.** Put the snapshot type and the comparison in `core/database-cardinality-feedback.ts` beside `FeedbackReplanState` (it reuses `rowCountSpread` and the same tuning); `core/statement.ts` is on the oversized list (`debt-oversized-source-files`) and should gain only the field, the capture call after compile, and the check call.

## Edge cases & interactions

- **Hysteresis and pacing** match overlay shifts: the 10× factor, the 1000-row floor (below it every plan is fast, and the sqllogic corpus never re-plans), the per-statement cooldown. Verify: the test below plus inspection.
- **Overlay-outranked counts.** An approximate module count sits below the overlay, so its drift does not move `plannedRowCount` while an observation answers — comparing planned counts, not raw module answers, gets this right without a special case. Verify: inspection.
- **Inside a transaction.** The store's count includes the transaction's buffered writes, so a bulk load re-plans statements at their next execution once it crosses 10× — desired. A rollback that shrinks the count 10× re-plans them back. Verify: inspection.
- **One-shot calls** (`db.get` / `db.eval` / `db.exec`) compile per call and need nothing. Verify: inspection.
- **Busy statements and concurrent committed reads**: the check runs only at execution start, after `tryRouteConcurrent` has decided on a compiled plan, exactly like the shift check today. Verify: inspection.
- **Per-execution cost**: one `plannedRowCount` per snapshotted table — a module call and at most one overlay lookup. Zero for statements over memory tables (no hook). Verify: `yarn bench --filter @store-mem` once before the change and once after in the same tree (foreground, well under 5 minutes each; no worktree A/B), compared with `--baseline`; no gated regression.
- **Option**: like module counts themselves, the drift check is not gated by `cardinality_feedback` (it is data-dependent, not history-dependent). Verify: inspection; doc.
- **Plans cached outside `Statement`** (materialized-view maintenance, assertion and watcher delta plans) still re-plan on schema change only, as §3.6 states. Verify: inspection.

## Tests (only this)

In `cardinality-feedback.spec.ts`, `describe('re-planning prepared statements')`: a memory-backed test module whose `getRowCount` reports an exact count the test sets. Prepare the `mid`/`big` join (`select m.x, b.w from mid m join big b on b.id = m.big_id where m.x = 1`; `big` on the test module, `mid` on the plain memory module and never analyzed) with `big` reported at 50 rows — hash `50 × 0.8 + 100 × 0.4 = 80` beats the seek plan's `100 × 1.8 = 180`, so no seek; set the report to 20,000; the next execution re-plans (plan shape: `Join` + `IndexSeek`, no `HashJoin`) and returns the same rows. Then a report move inside the 10× band (20,000 → 30,000) does not re-plan. Recompute the arithmetic against the tree when implementing — the unknown-side default in join selection is due to change in `unknown-size-join-scans-instead-of-seeking`.
