# Cardinality feedback: consume rows per key and re-plan on a shift

Second half of the rows-per-key slice; the observation side (`cardinality-feedback-rows-per-key-observe`) records a running mean of rows matched per key, per table and equality column set, in the overlay. This ticket makes planning read it and re-plan on a shift. The backlog ticket `feat-cardinality-feedback-beyond-table-size` names this slug as its prerequisite.

## Motivating case (from the plan stage, memory backend, never analyzed)

`parent` 2,000 rows, `child` 8,000 rows with an index `child_parent` on `parent_id`, four children per parent. `select p.name, c.note from parent p join child c on c.parent_id = p.id where p.name = 'p7'` plans a hash join over a full scan of `child` because the module guesses 10% of `child` per key: with `child` known at 8,000 that is 800 rows per seek, pricing the seek plan at `outer × (1.0 + 0.5 + 0.3 × 800)`. With the observed 4 rows per key the same candidate prices at `outer × 2.7` and wins; the measured run time was 5.9 ms for the hash plan against 1.24 ms for the seek plan.

## Where the estimate is consumed — the engine overrides its own readers, modules unchanged

`docs/optimizer-costing.md` requires a module's `rows` for a predicate to equal what the engine's provider would say for it; feeding observations to modules would need a new module-facing contract and every module to adopt it. So the module's own cost, its `rows`, and its seek-versus-scan arm choice stay in its currency and untouched (`filterInfo.indexInfoOutput.estimatedRows` keeps the module's number — `displacedPlan` and `probeModule` in `index-nested-loop.ts` compare module currency to module currency and must keep reading it). The engine overrides only where it consumes the estimate itself:

1. **The seam.** `RowCountSources` (`planner/stats/table-cardinality.ts`) gains `observedRowsPerKey(table, columns: readonly number[]): number | undefined` (a small sibling interface, `ObservedKeyCardinalities`, that `CardinalityFeedbackManager` implements; `databaseRowCountSources` forwards; the inline sources object in `plannedBefore` answers `undefined`). One exported reader, `plannedRowsPerKey(table, columns, sources)`, applies the precedence rule: when the catalog's statistics cover the column set — `table.statistics` with `rowCount > 0` and a `columnStats` entry for every column, by lowercase name, the same coverage rule as the memory module's `equalityTupleSelectivity` and the store's arm estimate — it returns `undefined` (the catalog wins and the module's statistics-backed estimate stands); otherwise it returns `max(1, round(mean))` of the valid entry, or `undefined` when there is none. The rounding floor matches the module's `Math.max(1, …)` and keeps a zero mean from pricing a seek at nothing. Reconsider the catalog-wins rule only after measuring; the count rule (newest exact wins) does not transfer to an average.

2. **`IndexSeekNode`.** In the constructor, snapshot `plannedRowsPerKey` once — like `TableReferenceNode.plannedRows` — for a site where `equalitySeekKeyColumns(filterInfo)` (the helper from the observe ticket) answers, reaching the sources through `source.schemaManager?.getRowCountSources()` (undefined for test-built nodes). Expose it as a readonly field. `computePhysical` relays it as `estimatedRows` when defined, else the module's number as today; the primary-key singleton branch is unaffected (a whole-key seek never has a snapshot). Clones (`withChildren`, `withProvenance`) recompute through the constructor; the compile is synchronous so the overlay cannot change between them.

3. **The index-nested-loop candidate.** In `tryIndexNestedLoop`, `rowsPerSeek = seek.plannedRowsPerKey ?? seekPlan.rows!` where `seek` is the rebuilt `IndexSeekNode` already in scope — the join key's column set is exactly that seek's equality set, so the one snapshot serves both readers. `perSeekLatencyMs`, `indexNestedLoopJoinCost` and the batched variant then read the observed number. The module-currency admission gate above it stays on `seekPlan.rows`.

Engine-side estimates over equality **filters** with no seek are not touched in this slice (they belong to `feat-cardinality-feedback-beyond-table-size`).

## Re-planning on a shift

In `recordRowsPerKey` (overlay), after folding a batch: when `rowCountSpread(mean, entry.baseline) >= cardinalityFeedback.shiftFactor` — the existing `(max + 1) / (min + 1)` spread, so 4 against a baseline of 800 is a shift and 80 against 100 is not — set `baseline = mean`, increment `shifts`, log under `core:cardinality-feedback` (table, columns, old baseline, new mean) and call `ctx.onShift(tableKey)`. The table key is what `Database.noteCardinalityShift` already fans out to statements whose plan reads the table (`Statement._noteCardinalityShift`, `planTableKeys`), paced by the existing `FeedbackReplanState` cooldown. No per-key marking is needed: a statement that reads the table re-plans and its seek nodes re-snapshot. A per-key entry's first record cannot shift when the plan already used the mean (baseline equals what the plan used); an entry re-created after eviction has the module's estimate as its baseline and may shift once, which lands the right plan.

## Edge cases & interactions

- Catalog statistics present for only some of the columns of a composite seek: the coverage rule falls back wholesale (observation answers) — mirrors both modules; by inspection, one assertion in the precedence test.
- `ANALYZE` after observations: swaps the schema, the entry is evicted, the module's statistics-backed estimate applies — by inspection (identity rule already tested for counts).
- A seek whose `source.schemaManager` is undefined (planner unit tests building nodes by hand): no snapshot, module number relayed — by inspection, type makes it `undefined`.
- The isolation module and other wrappers forward `getBestAccessPlan`; the override is engine-side so a wrapped table benefits without module changes — by inspection.
- Join candidate with a declined pushed predicate re-applied as a `Filter` above the seek: `rowsPerSeek` describes the seek alone, before the filter, exactly as the module's `rows` did — by inspection.
- Batched index-nested-loop (`atMostOne` proved): never on a non-unique seek, so never reads an override — by inspection.
- Mirrored candidate (seek the left, drive from the right): goes through the same `tryIndexNestedLoop`, so both orientations are priced with their own observed numbers — by inspection.
- `pragma cardinality_feedback = false` clears entries and stops observation; plans already cached keep their shape until recompile — by inspection, documented.
- A shift's `onShift` reaches every statement reading the table, including ones that never seek it; they re-plan once under the cooldown and land the same plan — accepted cost, say so in §3.6.
