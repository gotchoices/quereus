# Re-plan cached statements on a consequential size shift

Fourth of the `cardinality-feedback-*` chain (design: `docs/progressive-optimizer.md` §3.6). The overlay already records observed sizes and detects a **shift** — an observation at least `shiftFactor` (10×) from the table's baseline — and calls `onShift(key)`, which so far only logs. New compiles already read the updated overlay; this ticket makes long-lived prepared statements notice too.

## Why a full re-plan

The old design re-ran "only physical selection" on the cached plan. That cannot work here: cost-dependent decisions are spread over the Structural pass (`grow-retrieve`, `join-greedy-commute`, `fanout-lookup-join`, the materialized-view rewrite), the Physical pass (access path, QuickPick, aggregate strategy) and PostOptimization (join algorithm, key-set seek, merge join, nested-loop caching, conjunct ordering), and the Physical pass cannot re-run over an already-physical tree. A feedback re-plan is therefore exactly what a schema change already triggers: `Statement.invalidatePlan()`, then a rebuild from the retained AST at the next compile. Measured on one machine, a full compile costs 0.8–2 ms for simple statements and about 9 ms for a four-way join — paid once per shift per statement, bounded by the cooldown below.

## Design

### Broadcast (`core/database.ts`)

`Database` wires the manager's `onShift(key)` to a method that walks its existing `statements` set and calls `stmt._noteCardinalityShift(key)` on each. O(live statements) per shift; shifts are rare by construction (floor + 10× hysteresis).

### Statement side (`core/statement.ts` — keep the addition small; the file is on the oversized list)

- In `compile()`, after building, retain the plan's table dependency keys: lowercased `<schema>.<table>` for every `type: 'table'` entry of `dependencies.getDependencies()` (the same `BuildTimeDependencyTracker` result the schema-change listener already uses). Store as a `ReadonlySet<string>`; recomputed on every compile.
- `_noteCardinalityShift(key)`: if a plan is cached and its keys include `key`, mark it. Marking never touches the plan, the emission context or the scheduler — a running execution is never disturbed.
- At the start of `_iterateRowsRawInternal`, before `this.compile()`: ask the cooldown state whether a marked plan must be dropped now; if so, `this.invalidatePlan()`. A successful `compile()` clears the mark (the new plan read the current overlay), whatever caused the compile.

### Cooldown (`FeedbackReplanState`, exported from `core/database-cardinality-feedback.ts`)

A small class the statement holds, so the arithmetic is unit-testable away from `Statement`:

- `markShift()`; `onCompiled()` clears the mark; `onExecutionStart(cooldown): boolean` counts the execution and answers "drop the plan now?".
- The **first** feedback re-plan of a statement is immediate — its second execution should already run the corrected plan.
- Re-plan number `k + 1` (for `k ≥ 1` previous feedback re-plans) waits until the statement has executed at least `cooldown × 2^min(k − 1, 6)` times since re-plan `k`; a mark arriving earlier stays pending and fires at the first execution past the cooldown, not dropped.
- `cooldown` = new tuning field `cardinalityFeedback.replanCooldown` (default 8).

### One-shot paths

`db.get`, `db.eval` and `db.exec` compile on every call and so always read the current overlay; nothing to do.

## Edge cases & interactions

- **First re-plan is immediate.** Verify: the end-to-end test.
- **Cooldown arithmetic** — immediate first, 8 then 16 executions, multiplier capped at 64, early marks deferred not lost, compile clears a mark. Verify: unit test of `FeedbackReplanState`.
- **Unrelated statements are not touched** — a plan without the shifted table keeps its cached plan. Verify: inspection.
- **Busy statement** (mid-iteration) is only marked; the drop happens at its next execution start. Verify: inspection.
- **Plans over views and lenses** must carry the base tables' keys. Every table a statement resolves — including those inside an expanded view or lens body — goes through `resolveTableSchema` (`planner/building/schema-resolution.ts`), which records a `type: 'table'` dependency; only the view-mutation builder records `type: 'view'`. Verify: inspection that view bodies build in the statement's planning context (so their table dependencies land in the same tracker).
- **Multi-statement batches** (`nextStatement`) recompute the key set per compiled statement. Verify: inspection.
- **Concurrent committed reads** decide eligibility on a compiled plan (`tryRouteConcurrent`) before `_iterateRowsRawInternal` may re-plan; a re-plan of the same AST keeps the eligibility facts (read-only, the same tables and modules, no table-valued function). Verify: inspection.
- **Parameters**: the re-plan uses the statement's established parameter types, exactly like a schema-triggered recompile. Verify: inspection.
- **Auto-analyze in the test** would refresh `big`'s catalog statistics in the background and fix the plan itself, voiding the overlay entry. Verify: the test sets `pragma auto_analyze = false` before loading.
- **Plans cached outside `Statement`** (materialized-view maintenance plans, assertion and watcher delta plans) are not feedback-invalidated; they re-plan on schema change only. Verify: inspection; stated in the doc.

## Tests (only these)

In `packages/quereus/test/optimizer/cardinality-feedback.spec.ts`:

- **End to end:** `pragma auto_analyze = false; pragma cardinality_feedback = true;` tables `big (id integer primary key, v integer, w integer)` with 20,000 rows and `mid (id integer primary key, big_id integer, x integer)` with 300 rows (`big_id = (id * 7) % 20000 + 1`, `x = id % 5`), never analyzed. Prepare `select m.x, b.w from mid m join big b on b.id = m.big_id where m.x = 1`. Before the first run `getPlanShape().nodeTypes` has a `HashJoin` (over a full primary-key scan of `big`); run it (60 rows). The re-plan happens at the start of the next execution, not when the shift arrives, so `getPlanShape()` between the runs still reports the cached plan; after the second run (same 60 rows) the plan shape has a nested-loop `Join` and an `IndexSeek` and no `HashJoin`. (Measured on the memory backend at planning time: the flip happens with only `big`'s row count known; execution drops from 16.6 ms to 1.76 ms.)
- **Cooldown contract:** unit test of `FeedbackReplanState` as listed above.
