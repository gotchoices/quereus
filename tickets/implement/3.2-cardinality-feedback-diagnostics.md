# `cardinality_feedback()` and the user-facing docs

Fifth of the `cardinality-feedback-*` chain (design: `docs/progressive-optimizer.md` §3.9). Once the overlay is fed by execution, a user whose plan changed needs to see why. The old design wanted tier-selection reasoning in optimizer diagnostics; with tiers descoped (see the doc's rejected alternatives), what is worth surfacing is the overlay itself.

## Design

### Table-valued function `cardinality_feedback()`

No arguments. One row per **valid** overlay entry (its recorded `TableSchema` is still the catalog's current object — read through `CardinalityFeedbackManager.snapshot()`), ordered by schema then table:

| column | type | meaning |
|---|---|---|
| `schema_name` | text | |
| `table_name` | text | |
| `observed_rows` | integer | the count later plans use |
| `catalog_rows` | integer, nullable | `catalogRowCount` of the current schema (`ANALYZE`'s number), null when never analyzed |
| `baseline_rows` | integer | the value the next shift is measured against |
| `observations` | integer | complete enumerations recorded |
| `shifts` | integer | times a re-plan of dependent statements was signalled |

- Register it as **non-deterministic** (`deterministic: false`). Its output is session state; a deterministic zero-argument call is a constant-folding candidate, which would freeze the overlay into a cached plan at plan time.
- Advertise `(schema_name, table_name)` as its key (`relationalAdvertisement`), as the other introspection functions do.
- Put it in its own module under `func/builtins/` rather than `explain.ts` (1,099 lines). Like every TVF body it runs under the caller's exec mutex: it reads the manager directly and must never issue a nested `db.eval` / `db.exec`.
- With the option off the overlay is empty (disabling clears it), so the function returns no rows.

### Logging

One debug namespace, `core:cardinality-feedback`, naming each recorded shift (`table`, old baseline, new count) and each feedback re-plan (statement SQL prefix). Make sure the earlier tickets' log lines use it consistently.

### Docs

- `docs/functions.md` § Debug/Explain Functions: a row in the table and a columns subsection.
- `docs/usage.md` § Available Options: `cardinality_feedback` — what it does, default, that disabling clears learned sizes, that plans then depend on what ran earlier in the session.
- `docs/sql-txn.md` §9.5 ANALYZE: one paragraph on how cardinality feedback relates to `ANALYZE` and auto-analyze (a fresh `ANALYZE` supersedes an observation; observations cover tables auto-analyze cannot reach).
- `docs/progressive-optimizer.md` §3.9: present tense.

## Edge cases & interactions

- **No plan-time folding** of the function. Verify: test — a prepared `select table_name, observed_rows from cardinality_feedback()` returns no rows, then after a qualifying full scan of a 20,000-row table returns that table, without re-preparing.
- **Superseded entries are not listed** (an entry whose schema was swapped but not yet evicted). Verify: inspection — the TVF reads `snapshot()`, which filters on identity.
- **Option off** returns nothing. Verify: inspection.
- **Nested-query deadlock** cannot occur. Verify: inspection — no `db.eval` / `db.exec` in the body.

## Tests (only these)
