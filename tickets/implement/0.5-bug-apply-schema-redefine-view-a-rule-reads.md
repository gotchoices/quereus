Reported in GitHub issue #39 on 4.24.0, where the reporter's real schema has `TradingVariable`'s CHECK reading the view `TallyClosed`. Re-run on the current code with a temporary spec, on the memory module.

## Reproduction

From `table T (Id integer primary key, N integer); view V1 as select sum(N) as S from T; table P (Id integer primary key, U integer, check (U <= (select S from V1)));`, redefine `V1` as `select sum(N) + 1 as S from T` and keep the rest:

```
DROP VIEW IF EXISTS V1      -- cannot drop view 'main.V1': it is referenced by the CHECK constraint (U <= (select S from V1)) on table 'P'
create view V1 as select sum(N) + 1 as S from T
```

The database is restored intact, but the new schema can never be reached.

| what reads `V1` | today |
|---|---|
| unnamed or named CHECK, directly | refused |
| CHECK reading `V2`, a view over `V1` | refused: "reaches it through view 'V2'" |
| column DEFAULT | refused |
| assertion, directly | applies: the differ drops and recreates the assertion around the view (`namesDroppedObject`) |
| assertion reading `V2`, a view over `V1` | refused: `namesDroppedObject` looks at names written in the body only, while the guard follows views |

The same refusal hits a maintained table moving to another backing module (`DROP TABLE IF EXISTS m` followed by its recreate) with a CHECK reading `m`. It was run with `allow_destructive = true` and refused with `cannot drop table 'main.m'`.

## The rule

A forward drop passes the expression guard when **this plan recreates that same object**: the name is in both the drop bucket and the create bucket (`viewsToDrop` and `viewsToCreate`, or `tablesToDrop` and `tablesToCreate`). Otherwise the guard stays on.

This keeps the refusal that matters. A declaration removing `V1` while the CHECK still reads it is still refused, and that case must be covered by a test. So is removing a mid-chain view while the CHECK still reaches it. A hinted view rename is a different name on each side, so it gets no exception.

## Design

**The exception.** Add a scope on `Database` modelled on `_setSchemaUnwinding`, holding the recreated objects' `objectRefKey`s, set in `emitApplySchema` beside `_setSchemaMigrating` around `runBatchedMigrationLoop`. A small exported function in `schema-differ.ts` computes the set from the diff (for example `objectsRecreatedByDiff(diff, schemaName)`). `assertNoExpressionDependsOn` returns early when the object's key is in it.

**Assertions keep their guard.** Widen `namesDroppedObject` so that a body reaching a dropped object through declared views and declared maintained bodies also counts, reusing the declared-view walk from `bug-apply-schema-view-chain-order`. The assertion is then dropped first and recreated last, as in the direct case, and `CREATE ASSERTION` plans its body at build time, so a new view that no longer satisfies it fails loudly. An assertion in another schema is not in this catalog, so it still refuses the drop; say so in the docs.

**Re-validation.** After the last step, and only when the set is non-empty, `runStepsWithUndoJournal` checks each CHECK that reaches a recreated object, across every schema (a new query in `expression-dependents.ts`, built on `reachableObjects` and one `snapshotObjectRefResolvers` snapshot, like `findTableExpressionDependent`). It runs `rejectCheckViolatedByExistingRows`, changed to take `db` and exported, so the `permitsGrandfatheredCheckViolators` opt-out and the row-invariant filter apply exactly as for `ADD CONSTRAINT`. A failure takes the failed-step path: unwound when the journal is clean, otherwise `describeIrreversible(poisonedBy)`. Its message must name the CHECK and say that a recreated object caused it, with the original error as `cause`. A CHECK this plan just added may be scanned twice, which is harmless.

## Why this matches a user-issued redefinition

There is no statement that replaces a view in place. A user must run `alter table P drop constraint pc; drop view V1; create view V1 ...; alter table P add constraint pc check (...)`, and each row below was run:

| user statement, against a view that lost or tightened the column | result | what the apply must do |
|---|---|---|
| `add constraint` with rows that now violate | `CHECK constraint failed: pc — existing rows in 'P' violate the constraint` | same, through `rejectCheckViolatedByExistingRows` |
| `add constraint` on an empty table, column `S` gone | `Column not found: S` | same: the validation scan plans the expression whatever the row count |
| `add constraint ... check on insert`, column gone | accepted | same: not a row invariant, so filtered out and not scanned |
| `alter column set default ((select S from V1))`, column gone | accepted | same: no check |

So a DEFAULT, and a CHECK that is not a row invariant, get no check, and a new view that lost the column surfaces on the next write that uses them. Leave a `NOTE:` tripwire at the re-validation site saying so. A generated column reading a view also gets no check, and no user statement redefines one. This was read from the code, not run.

## Alternatives rejected

- **Stand the guard down for every forward step** (the issue's suggestion). A declaration that removes the view and keeps the rule would apply and leave the table unwritable.
- **Drop and re-add the CHECK around the view**, as the differ does for assertions. It would keep the plan plain runnable DDL. But a table-level unnamed CHECK has no stored name, so no statement can drop it (`diffUnnamedConstraints`), and that is the issue's exact shape. A generated column has no equivalent either.
- **Replace the view in place.** Forward order needs `V1` before `V2`, and the reversed undo would plan `V2`'s old body against `V1`'s new one, which may have lost a column. Drop and create has no such conflict, and no replace statement exists.

## Facts already checked

With `V1` dropped and the CHECK on `P` in place, each of these succeeded on the memory module with a row in `P`, so the stretch of the plan where the view is absent is safe: `add column` (with and without a default), `set not null`, `set data type`, `set default`, `rename column`, `drop column`, `add constraint`, `alter primary key`, `create index`. Only a write fails (`insert` gives `Table 'V1' not found`), and a plan writes rows only for seeds, which run after the views are back.

## Known limits to document

- `diff schema` output run by hand is refused at the `DROP VIEW`, because the exception exists only inside `apply schema`. The refusal names the CHECK, which is the user's way forward.
- A view removed together with the rule that reads it is still refused. That is a plan-order problem filed separately as `bug-apply-schema-refuses-view-removed-with-its-check`.
