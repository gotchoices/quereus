# Bare store: non-committing DDL ignores the coordinator's restorable states

## Context

`bug-rolled-back-rows-violate-surviving-ddl` establishes the rule: row-validating DDL inside a transaction judges the rows the transaction can see (for `CONSTRAINT` / `MISMATCH`) **and** every state a rollback could restore (committed rows, plus the rows at each open savepoint taken before the DDL), refusing with `BUSY` and a "commit the pending writes first" message when a restorable state would violate the new rule. That ticket implements the rule for the memory backend, the isolation wrapper, and the store **behind** the wrapper, where the store's own rows are exactly the committed rows and the wrapper supplies the savepoint states.

This ticket covers the store used **without** the wrapper (`StoreModule` directly). There the transaction's writes are buffered in the module-wide `TransactionCoordinator` as an op log (`pendingOps`) with savepoints recorded as positions into that log (`savepointStack[i].opIndex`). The store's effective stream (`iterateEffectiveEntries`) merges the committed entries with the last-write-wins index over the whole log, so it sees exactly what a `select` sees, and nothing else.

## Which arms are affected

The store's row-rewriting ALTER arms (`set data type`, `set not null` with a backfill, `set collate` over a covered unique structure, every primary-key re-key) call `ddlCommitPendingOps()` before mutating: the buffered writes become durable at DDL time (the declared `'auto-commit'` tier), so afterwards there is no restorable state and nothing to check. These arms need no change.

The non-committing arms do have the hole (inferred from the code; not run, since the bare module is not in the default test matrix):

- `createIndex` with `unique`: `buildIndexEntries` reads the effective stream and its in-pass duplicate check judges only that stream. A committed row the transaction deleted is neither checked nor indexed. After `rollback` the row is back, the index has no entry for it, and `findUniqueConflictViaIndex` trusts the index to hold every live row, so a later duplicate is accepted silently.
- `alterAddConstraint` with `unique`: `validateUniqueOverExistingRows` over `effectiveDdlRows(table)` only.
- `alterColumnSetNotNull` when no NULL is visible: `rowsWithNullAtIndex` reads the effective view; the change is then metadata-only and commits nothing, so an overwritten committed NULL (`update … set v = 'x'` then `set not null`) comes back on rollback.

## Design

- `TransactionCoordinator`: a way to view the pending ops **as of a savepoint**, i.e. the last-write-wins buckets rebuilt from `pendingOps.slice(0, savepointStack[i].opIndex)`. `rebuildPendingIndex` already replays the log into buckets; generalize it to a prefix length and return a bucket map without installing it. Expose "the ordered pending ops for `store` at savepoint depth `i`" and the number of open savepoints.
- `StoreTableBase.iterateEffectiveEntries`: accept an optional pending-ops view so the same merge can run over a savepoint prefix (and over no pending ops at all, which is the committed state — `store.iterate` directly, as `StoreTable.validateRekeyedPrimaryKey` already does for its `BUSY` probe).
- A store-side counterpart of the memory manager's "judge each restorable state, rewrap as `BUSY`" helper in `store-module-index-build.ts`, yielding: the committed rows, then one stream per open savepoint. Wire it into `createIndex` (unique), `alterAddConstraint` (unique), and `alterColumnSetNotNull`'s no-visible-NULL path. Reuse `validateUniqueIndexOverRows` / `validateUniqueOverExistingRows` for the probes; the NOT NULL probe is a NULL scan.
- The wrapped leg must not double-judge: when `rows` (the wrapper's `IssuerRowSources`) is supplied, the coordinator holds no ops for this table, so the committed state is the only coordinator-side state and the savepoint states come from `rows.savepoints`. Make the helper take the wrapper's list when present and the coordinator's prefixes otherwise, so the arms have one call site each.

## Tests

- One bare-`StoreModule` spec per arm (pattern: `packages/quereus-store/test/alter-pending-ops.spec.ts`): buffered delete then `create unique index` then `rollback` refuses with `BUSY` matching `/commit the pending writes first/i`; the same with a savepoint-then-delete-then-`rollback to`; `update … set v = 'x'` then `set not null` refuses; and the legal shape (deleted row breaks no rule) stays accepted and survives the rollback cleanly. Verify each refusal leaves the transaction usable and that `commit` followed by the same DDL succeeds.
