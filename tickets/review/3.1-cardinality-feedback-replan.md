# Re-plan cached statements on a consequential size shift — review handoff

Fourth of the `cardinality-feedback-*` chain. The overlay already detected a **shift** (an observed table size at least `shiftFactor` = 10× from its baseline) and called `onShift(key)`, which only logged. Prepared statements now act on it.

## What landed

- **Broadcast** — `Database.noteCardinalityShift(key)` (`core/database.ts`) is the manager's `onShift`; it walks the live `statements` set and calls `stmt._noteCardinalityShift(key)` on each.
- **Statement** (`core/statement.ts`, +~40 lines):
  - `compile()` keeps `planTableKeys`: lowercased `<schema>.<table>` of every `type: 'table'` dependency from the builder's `BuildTimeDependencyTracker` (helper `tableDependencyKeys`). View bodies build in `storedBodyContext(...)`, a spread of the statement's planning context, so their base tables share the tracker.
  - `_noteCardinalityShift(key)` marks only when a plan is cached and reads `key`. It never touches the plan, emission context or scheduler.
  - `dropPlanOnShift()` runs in `_iterateRowsRawInternal` right before `compile()`: asks the cooldown state and, if due, logs (`core:statement`) and calls `invalidatePlan()`.
  - `invalidatePlan()` now also calls `feedbackReplan.onPlanDropped()`.
- **Cooldown** — `FeedbackReplanState` (exported from `core/database-cardinality-feedback.ts`): `markShift()`, `onPlanDropped()`, `onExecutionStart(cooldown): boolean`. First feedback re-plan immediate; re-plan `k+1` needs `cooldown × 2^min(k−1, 6)` execution starts since re-plan `k`, counting the re-planning execution itself. Early marks stay pending.
- **Tuning** — `cardinalityFeedback.replanCooldown` (default 8) in `planner/optimizer-tuning.ts`.
- **Doc** — `docs/progressive-optimizer.md`: status line, §3.6 (present tense, mechanics, the mark-clearing rule), §3.9 (which log names what; `getPlanShape` shows the cached plan until the next execution), §6 key files.

## Deviation from the ticket — flag for review

The ticket said "a successful `compile()` clears the mark". The code clears it on **plan drop** (`invalidatePlan` → `onPlanDropped`) instead. A cached plan can only be replaced by going through `invalidatePlan` (the initial compile has no plan, so nothing to mark), so the two say the same thing for marks on a live plan. The difference: with clear-on-compile, a schema change landing between a shift and the next execution would leave the mark set. `onExecutionStart` would then count a redundant "feedback re-plan" (an `invalidatePlan` on an already-dropped plan), which lengthens that statement's later cooldowns for no reason. Clearing on drop avoids that. The unit test asserts the drop-clears behaviour.

## Tests added (`test/optimizer/cardinality-feedback.spec.ts`)

- **`re-plans at the execution after the one whose scan shifted a table it reads`** — end to end: `big` (20,000 rows) and `mid` (300) never analyzed, `auto_analyze` off, `cardinality_feedback` on. ## Inspection points for the reviewer (no test, by design)

- **Unrelated statements** keep their plan: the `planTableKeys.has(key)` gate.
- **Busy statement**: the shift is published in the run site's `finally`, often for the very statement that observed it, and only marks. The drop happens at its next `_iterateRowsRawInternal`.
- **Batches**: `nextStatement()` → `invalidatePlan()` → the next `compile()` recomputes the keys.
- **Committed reads**: `tryRouteConcurrent` compiles and decides eligibility before `_iterateRowsRawInternal` may re-plan. A re-plan of the same AST keeps the facts eligibility rests on (read-only, the same tables and modules, no table-valued function).
- **Parameters**: the re-plan goes through `compile()` with the statement's established parameter types, the same as a schema-triggered recompile.
- **Key match**: `resolveTableSchema` records `schemaName: tableSchema.schemaName, objectName: tableSchema.name`, the same fields the manager's `tableKey` lowercases.
- **Not feedback-invalidated**: plans cached outside `Statement` (materialized-view maintenance, assertion and watcher delta plans). They re-plan on schema change only, as §3.6 states. Statements prepared internally through `db.prepare` (for example the foreign-key probe cache) are in `statements` and do re-plan.

## Known gaps / things worth a second look

- `dropPlanOnShift` counts an execution even when that execution later throws before running (a compile error, for example). Harmless for pacing, but the count means "execution starts", not "successful executions".
- `onShift` runs synchronously inside `publish` and walks every live statement. That is O(live statements) per shift, and shifts are rare by construction. There is no NOTE tripwire because the doc's overhead section (§3.8) already states this cost.
- The re-plan log line calls `getBlockSql()` (an AST stringify). It runs only when a re-plan actually happens.
- `yarn test:store` was not run. The change does not touch the store path, but the end-to-end behaviour on the LevelDB store is unverified.
