# Store providers can declare a per-row read latency — review handoff

Mirrors the first-row hint path end to end for `expectedRowLatencyMs` (wall-clock ms per row after the first, sequential iterate).

## What changed

- `KVStoreProvider.expectedRowLatencyMs?: number` (`kv-store.ts`), doc'd beside `expectedLatencyMs`.
- `resolveExpectedLatencyMs(declared, field = 'expectedLatencyMs')` (`cost-profile.ts`) — generalized with a `LatencyField` name param used only in the warning text. Default keeps existing call sites/tests unchanged. `LatencyField` type is not re-exported from the package index (not needed by callers today).
- `StoreModuleBase.expectedRowLatencyMs` resolved at construction.
- `IsolationModule.expectedRowLatencyMs` live forwarding getter (underlying's value or 0). Only the getter + doc comment added to that oversized file.
- LevelDB / IndexedDB provider NOTEs now say both hints are declined and why; IndexedDB NOTE dropped the "surface lands with this ticket" clause.
- Docs: store README new "Backend per-row latency" paragraph; isolation README forwarding list; `module-capabilities.md` row filled in; `progressive-optimizer.md` §5 item removed; `optimizer-costing.md` sentence that pointed at this ticket updated.

## Test added

- `expected-latency-plan.spec.ts` › "per-row latency reaching the planner" › "seeks with a declared per-row latency, hashes without one": isolated store module (`createIsolatedStoreModule`) over in-memory provider, 30 ms first-row; 50-row memory outer × 5,000-row store inner on PK. With 1 ms/row → `Join` over `IndexSeek` (index-nested-loop), no `HashJoin`; first-row only → `HashJoin`, no `IndexSeek`. Arithmetic in the spec comment (hash 32,040 vs INL 1,500,090 without per-row; hash 5,032,040 vs INL 1,550,090 with). Proves provider → StoreModule → IsolationModule → planner.

No separate resolver tests for the new field — shared resolver's rule already covered by the existing first-row cases.
