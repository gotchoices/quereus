# Record how to undo each migration step — implemented

## What landed

`generateMigrationPlan(diff, schemaName?, actual?)` takes the pre-apply `SchemaCatalog` as an optional third argument. With it, every `MigrationStep` carries either `undo: readonly string[]` (the statements that put the catalog back, in execution order; `[]` when the step changes nothing) or `irreversible: string` (a user-readable reason). Without it nothing about the undo is computed — `generateMigrationDDL` is unchanged and the `diff schema` text is pinned byte-for-byte against the pre-change output (captured from HEAD before editing, for both `main` and a non-main schema).

The undo is rendered at each forward step's own push site by a new `UndoRenderer` class at the bottom of `schema-differ.ts`, so a step and its reversal read together. The renderer is told about renames as their steps are pushed and reads the pre-apply catalog *through the renames in force at that step*, which is what makes both of the ticket's rules hold.

Every arm of the ticket's table is filled in. Three steps are irreversible, exactly the data-destroying ones (`DROP TABLE`, `DROP COLUMN`, `SET DATA TYPE`), gated on the target existing in the pre-apply catalog (a `DROP TABLE IF EXISTS` of an absent table undoes to `[]`).

## Where this deviates from the ticket text, deliberately

- **Rule 2 is applied more precisely than written.** The ticket says to forward-apply "this diff's" renames to catalog-sourced bodies. That is wrong for a body restored *before* the column-rename phase: a view dropped in step 5 is undone after the `RENAME COLUMN` in step 11 has already been reversed, so its restored body must use the *old* column name. The renderer therefore applies exactly the renames whose steps precede the current step (table renames are always in force; column and constraint renames from the point their step is pushed). This is Rule 1 taken seriously, and it is what the ticket's own "view dropped in a diff that renames a source table" case needs. Pinned by the test "only renames whose steps PRECEDE the step count".
- **`SET MAINTAINED` in the reshape leg undoes to `DROP MAINTAINED`, not to the prior derivation.** When the same plan detached the table earlier (`dropMaintained` + `setMaintained` on one alter), the table is *plain* at the re-attach step, so its undo is a detach; the earlier detach's own undo restores the original derivation. Together they compose back, which is what the ticket asked for; the ticket's table row reads as if "actual maintained" alone decided it. Pinned by "the reshape leg … compose back".
- **`SET DEFAULT` after a `dropStaleDefaultFirst` clear undoes to `DROP DEFAULT`**, not to the pre-apply default: the column reaches that step with no default. Moot in practice (the retype between them poisons the journal) but Rule 1 requires it. Pinned.
- **The catalog grew three optional fields** rather than the renderer parsing catalog `ddl` text: `namedConstraints[].bodyAst` (full-fidelity lift; the canonical `definition` has already dropped FK deferrability), `maintained.columns` (the recorded explicit column list, needed to render `set maintained (cols) as`), and `CatalogView.columns` (the explicit column list; `CatalogView.ddl` is not a reliable re-parse source — see "For ticket 2"). Each is destructured-and-ignored in `renderCatalogForComparison` with a comment saying why (already folded into `definition` / `bodyHash`). Only the index arm parses text, because the catalog carries no structured index shape: it re-parses `generateIndexDDL`'s output with the real parser, re-targets the table at its current name, and re-renders through `createIndexToString` + `applyIndexDefaults`, the same path the forward index creates take.
- **Restored bodies are spelled in the persisted-DDL form, not the declared form.** A restored CHECK reads `check on insert, update (…)`, a restored FK carries `on delete restrict on update restrict`, a restored index column carries `collate binary`. That is exactly what `generateTableDDL` / `generateIndexDDL` already persist and re-parse, so no new normalizer was written; the round-trip tests execute these statements and prove the catalog rendering comes back identical.

## For ticket 2 (apply-schema-rollback-journal)

- **`ViewSchema.sql` is not stable across a rename.** `create view` stores the full statement text; the table- and column-rename propagation overwrite it with the rewritten body alone, and `CatalogView.ddl` is that field verbatim, rendered by `renderCatalogForComparison`. Verified: `create view v as select id from a` → after `alter table a rename to b` the field reads `select id from b`. So any plan with a table rename and a dependent view will not render equal to the pre-apply fingerprint after a correct unwind. I appended this as an edge-case arm to ticket 2's body with the two ways out (compare with view `ddl` blanked — what this ticket's round-trip `fingerprint` helper does — or make the propagation regenerate the full statement). The reviewer should not treat the round-trip helper's blanking as a test loosening; it is working around that pre-existing drift, and the helper's comment says so.
- The reason strings are written for the executor's diagnostic: `dropping table "t" also discards its rows, and no statement can bring them back`; `dropping column "c" from table "t" discards the values stored in it, …`; `changing the type of column "c" in table "t" converts the values stored in it, and a conversion can lose information …`; and `<step> cannot be undone: <why>` for a catalog entry the renderer cannot rebuild from.

## Known gaps and things a reviewer should push on

- **Cross-table CHECK subquery under a same-diff column rename** (the `'foreign'` branch of `replayRenames`) is implemented by mirroring the live non-owning propagation but has no direct test; the tested paths are the owning-table seeded rewrite, the FK parent column list, and table renames inside view / assertion / CHECK bodies. The mid-replay cursor that `resolveColumnNow` uses (so the resolver sees only the renames replayed so far) is exercised only indirectly.
- **`view.select` / `assertion.check` absent** and **`maintained.select` absent** paths are reachable only from hand-built catalogs; they return `irreversible` with a reason (tested for the constraint and index arms, not those two).
- **Non-main schema** is tested with a hand-built catalog only (there is no live-DB case for `analytics.`-prefixed undo text). The prefix logic reuses the forward creates' `apply*SchemaDefault` helpers, so drift there would show in the forward path too.
- **Index name shared by two tables**: the renderer keys indexes by bare name and the first entry wins, matching what the plan's bare `DROP INDEX` does. Tagged `NOTE:` in the `UndoRenderer` constructor.
- **Undo is rendered eagerly at plan time**, so once ticket 2 passes the catalog every apply pays it; the per-step cost is one small parse on the fragment arms (dropped index, added column, added constraint). Tagged `NOTE:` on the class doc; render lazily if plan generation ever shows in profiles.
- **`generateMigrationPlan` still reads `diff.tablesToCreate` and the other create buckets without `?? []`**, as before; the tolerance the ticket asked for is on the alter sub-buckets (`?? []`, unchanged) and on catalog lookups (absent object → `[]`).
- No arm currently needs more than one undo statement, so "several statements in order" is supported by the type and the executor contract but has no producer and no test.
