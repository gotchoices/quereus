# Review: re-plan cached statements when a module-reported row count drifts

## What was built

A prepared statement now re-plans when a table size reported by the table's module (`VirtualTableModule.getRowCount`, e.g. the store's running count) moves 10× or more from the size its cached plan was costed with. Before this, nothing caught it: overlay shifts come only from complete scans, a seek plan never makes one, and a complete scan of a module-sized table compares against the live count, so it never reports a shift.

- **`ReportedSizeSnapshot`** (`core/database-cardinality-feedback.ts`, beside `FeedbackReplanState`).
  - `capture(db, dependencies)`: for each `table` dependency whose module implements `getRowCount`, it keeps `{ table: TableSchema, rows: plannedRowCount(table) ?? defaultRowEstimate }`.
  - `drifted(db)`: true when some kept table's current planned count satisfies `spread(now, then) >= shiftFactor && max(now, then) > minRows`, which is the overlay's shift rule. It skips a table whose catalog object has been replaced. It logs each drift on `core:cardinality-feedback:debug`.
- **`moduleReportsRowCount(db, table)`** (`planner/stats/table-cardinality.ts`): tells whether the module has the hook, whether or not it answers right now. A store table that declines before its count is loaded is still kept, so the count that arrives later can still trigger a re-plan.
- **`Statement`** gained only the following:
  - a `reportedSizes` field;
  - a capture in `compile()` right after `optimize` (same synchronous turn, so the counts match what the plan's `TableReferenceNode`s saw);
  - a reset in `invalidatePlan()`;
  - one line in `dropPlanOnShift()` that calls `markShift()` on drift before the cooldown decides (`FeedbackReplanState.onExecutionStart`).
- Docs: `progressive-optimizer.md` §3.6 now describes the second trigger. §3.7 "Module counts in cached plans" and the Determinism note say the option does not gate it. §3.8 has the overhead measurement, §3.9 the debug log, §6 the key files, and the §5 item is removed. `store.md` got one sentence.

## Test added

- `cardinality-feedback.spec.ts` › `re-planning prepared statements` › *re-plans when a module-reported size drifts 10x from the one the plan was costed with*. Setup: `big` is on a memory subclass whose `getRowCount` returns whatever the test sets; `mid` is a plain memory table. With `big` reported at 50 the plan is `HashJoin`. After setting the report to 20,000, the next execution re-plans to `Join` + `IndexSeek` and returns the same 60 rows. After moving the report to 30,000 (1.5× from the new snapshot, but 600× from the first one) the plan object stays the same (`stmt.compile()` identity). The test sets `replanCooldown: 1` so the cooldown cannot be what keeps the plan. I confirmed it fails with the drift line disabled.

## Known gaps / things to look at

- **Write targets are kept too.** Every `table` dependency is kept, including the target of an `insert`. So a prepared `insert into t values (?)` driving a bulk load re-plans at roughly 1k, 10k, 100k, … rows, paced by the cooldown. Each re-plan is cheap and it is what the ticket asked for, but the plan does not depend on the target's size. Filtering to read dependencies would need the builder to record read vs write, which the dependency tracker does not do today.
- **Drift stays true until the re-plan.** During a cooldown wait, `drifted` re-runs at every execution start and repeats its debug log line each time. The cost is the same as a no-drift check.
- **Unknown reads as `defaultRowEstimate` (1000).** Join selection currently prices an unknown side at 100 (`unknown-size-join-scans-instead-of-seeking`). So "what the plan used" for a declining module is approximate. Because of the floor, a decline-then-count of ≤ 1000 rows never drifts.
- **Test arithmetic depends on the tree.** It was checked by running the test, not recomputed from the cost formulas. `mid` is a never-analyzed memory table, so the fix ticket `unknown-size-join-scans-instead-of-seeking` may change the initial plan at 50 rows from `HashJoin` to a seek. If it does, the first assertion needs a smaller reported size or a different shape.
- **Not covered by tests, checked by reading the code only:** the overlay outranking an approximate count; transaction and rollback behaviour; the skip for a replaced catalog object; plans cached outside `Statement` (materialized-view, assertion and watcher plans re-plan on schema change only); concurrent committed reads (the check runs after `tryRouteConcurrent`, like the shift check).
