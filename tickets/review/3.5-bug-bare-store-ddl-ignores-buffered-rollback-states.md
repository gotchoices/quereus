# Bare store: non-committing DDL vs. the states a rollback could restore

## What changed

**Refusal.** Without the wrapper, `create unique index`, `add constraint … unique` and a `set not null` that sees no NULL now judge the committed rows and the rows at each open savepoint, after judging the visible rows. A violation only in a restorable state refuses with `BUSY` ("Commit the pending writes first, then retry."). A violation the transaction can see keeps `CONSTRAINT`. When nothing is buffered for the table, no extra scan runs.

**Arms that flush are exempt.** `set data type` conversion and the UNIQUE re-validation of `alter column` use `judgeRollbackStatesBeforeFlush`, which judges only a wrapper's states. Their flush makes the writes durable and ends the savepoints, so nothing is left to restore.

**Index population (beyond the ticket's design; please scrutinize).** The ticket's "legal shape survives the rollback cleanly" could not be met by judging alone, because the index build read only the visible rows. The repro confirmed that after `delete` + `create unique index` + `rollback`, a duplicate of the restored row was accepted silently. Adding the restored rows to the index directly is not safe either: an overwritten row would keep two entries, and a range or ordered index scan yields that row twice (`scanIndex` has no dedup outside multi-seek).

So `populateIndexStore` now writes physical entries for committed rows only. It queues the ops the transaction's buffered writes owe the new index through the coordinator, each spliced right after its data op so it sits before any later savepoint (`TransactionCoordinator.queueDerivedOps`). Commit, rollback and rollback-to each leave the index as if it had existed when the transaction began. Consequences:

- Plain `create index` gets the fix too; it shares the path and had the same missing-entry wrong result.
- The hidden `_uc_*` store built by `add constraint` goes through the same path (`reconcileImplicitUniqueIndexStores`).
- This removes the old comment claiming stale entries are harmless, which was false for range and ordered scans over a live row.
- A failed `create index` now discards its queued ops before teardown, or the later commit would write into a closed store (`discardQueuedIndexOps`).

## Decisions to check

- **`set not null` with a usable DEFAULT and a NULL only in a restorable state takes the backfill rather than refusing.** The backfill's flush ends the states holding the NULL, so it cannot come back. This matches the rule the prereq set for the memory backend and the wrapper, but it means a statement that used to stay inside the transaction now commits it. Refusing with `BUSY` would be the conservative alternative: every bare state's `backfilled` flag would become false, and the committed-rows meaning of that field would need rewording.
- **Two existing tests were removed because they pinned the behaviour this ticket replaces:** `honors a pending delete of the only NULL row` (`alter-pending-ops.spec.ts`) and `ADD CONSTRAINT UNIQUE accepts when a pending DELETE removes the committed duplicate` (`unique-constraints.spec.ts`). Both accepted a statement that a rollback could then violate. The same shapes are now asserted as `BUSY` in the new spec.
- **`iterateEffective` is no longer a generator.** It reads the pending view when called rather than at first `next()`, which avoids a second async-generator layer on the hot scan path. All four call sites consume it immediately, checked by reading them.
- The ticket's "number of open savepoints" accessor was not needed; `getOrderedPendingOpsAtSavepoints` returns one view per savepoint.

## Known gaps

- **The bare path has not run on real LevelDB or IndexedDB.** The new spec uses an in-memory provider, and `test:store` goes through the isolation wrapper. The queued ops use the same `ensureIndexStore` handle as ordinary index maintenance, so I expect no provider difference, but that is from reading the code, not from a run.
- **`add constraint` with FOREIGN KEY or CHECK** does not judge restorable states here. The ticket does not list them and I did not check whether they have the same hole.
- **PK re-key** keeps its committed-rows `BUSY` probe in bare mode even though its flush leaves nothing to restore, so it can refuse a safe statement. This predates the ticket, which says the rewriting arms need no change, and `docs/store.md` still describes the probe.
- **Contrived corner, inferred from code and not run:** a UNIQUE constraint whose name equals an explicit index on other columns gets no `_uc_*`. A collation-only `set collate` could then skip the flush while skipping the rollback-state judgement as well.
- **Scan cost, counted by reading the code:** a bare `create unique index` with buffered writes and S open savepoints makes S + 3 full scans (visible rows, committed rows, each savepoint, the build). A `NOTE:` on `bufferedRollbackScans` records the possible optimization.

## Tests

New file `packages/quereus-store/test/bare-ddl-rollback-states.spec.ts`, 26 tests. Run against the unfixed code first: the refusal, enforce-after-rollback and restored-lookup tests failed there, reproducing the bug on every arm.

Run for both `create unique index` and `add constraint unique`:

| Test | Verifies |
| --- | --- |
| refuses when a committed duplicate would come back on rollback | `BUSY`, transaction still usable, same DDL succeeds and enforces after commit |
| refuses when only an open savepoint holds the duplicate | The savepoint state is judged on its own; `rollback to` still works |
| stops refusing once the savepoint holding the duplicate is released | A released savepoint is not a restorable state |
| keeps CONSTRAINT for a duplicate the transaction can see | The visible pass runs first |
| accepts a deleted row that breaks no rule, and enforces against it after rollback | The silent-duplicate repro |
| enforces the rows of the savepoint a rollback-to restores | Derived ops sit at their historical log positions |
| frees the value of a row the committed transaction deleted | No leftover entry blocks the value after commit |

`create index` over overwritten and deleted rows:

| Test | Verifies |
| --- | --- |
| finds the restored values after rollback | Restored rows are indexed |
| leaves no second entry for an overwritten row after rollback | No duplicate from a range scan |
| leaves no second entry for an overwritten row after commit | Guards against the direct-write design |
| reads its own writes through the new index | Pending index ops are visible in the transaction |

`set not null`:

| Test | Verifies |
| --- | --- |
| refuses when a committed NULL the transaction overwrote or deleted would come back | `BUSY`, and it succeeds after commit |
| refuses when only an open savepoint holds the NULL | Savepoint state is judged |
| keeps CONSTRAINT for a NULL the transaction can see | The visible pass runs first |
| takes the committing backfill when a DEFAULT can fill a restorable NULL | The decision above |
| accepts when no state holds a NULL, and stays inside the transaction | No needless commit |

Other:

| Test | Verifies |
| --- | --- |
| retypes past a deleted row that could not convert | A flushing arm judges no rollback state |
| recollates past a deleted row that would collide | Same, for the UNIQUE re-validation |
| a failed create index leaves nothing queued against its torn-down store | The failure unwind |

Mutation checks, both reverted afterwards: removing the discard fails the unwind test, and appending derived ops at the log tail fails the rollback-to test on both arms.

## Usage

```sql
-- committed rows: (1,'a'), (2,'a')
begin;
delete from t where id = 2;
create unique index ux on t (v);  -- BUSY: the deleted row would come back as a duplicate
commit;
create unique index ux on t (v);  -- succeeds

-- committed rows: (1,'a'), (2,'b')
begin;
delete from t where id = 2;
create unique index ux on t (v);  -- accepted, row 2 breaks no rule
rollback;                         -- row 2 is back and indexed
insert into t values (3, 'b');    -- CONSTRAINT
```
