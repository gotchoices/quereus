# SQL ALTER — Rename Propagation

> **Stability: Stable** — see [Stability Tiers](stability.md#tiers).

How `ALTER TABLE … RENAME TO` and `RENAME COLUMN` carry a name change through the objects that
depend on it: which references are rewritten, how a reference is decided to be one, and when the
statement is refused. A satellite of [SQL Schema Modification — ALTER](sql-alter.md), which has
the syntax of both verbs.

## RENAME TABLE

References to the old name in dependent objects are rewritten in place: CHECK expressions on every table in the schema, FOREIGN KEY `referencedTable` entries (across all schemas), partial-index `WHERE` predicates (a table-qualified self-reference like `where t.active = 1` follows the rename, including in the derived UNIQUE constraint of a unique partial index, which shares the predicate AST), the two expressions a **column** carries — a `DEFAULT` and a `GENERATED ALWAYS AS` body — on every table in every schema (each reaches another table only through a subquery, `w integer default ((select min(v) from u))`; the renamed table's own self-referencing default is rewritten before the catalog swap, so nothing ever observes a default naming the vanished name), view bodies (`selectAst` and the cached `sql` text), view/MV `with defaults` clauses (now stored inside the body select, so an expr subquery referencing the renamed table is rewritten by the body walk — a clause-only rewrite still fires the modified event), materialized-view bodies (which additionally re-key their derived fields and re-register row-time maintenance, staying live — see [mv-schema-change.md § Rename propagation](mv-schema-change.md#rename-propagation-mv--faster-view)), and assertion CHECK expressions (the stored expression is rewritten and its derived violation query regenerated, so the assertion keeps enforcing the same rule against the renamed table). The rewrite is scope-aware: a name the dependent body itself binds — a `with` clause CTE, a FROM alias, an aliased subquery or function source, an `update`/`delete` target's correlation name — is not a reference to the renamed table and is left untouched (a view body `with t as (select …) select … from t` keeps reading its own CTE after `alter table t rename to t2`), while a schema-qualified `main.t` inside such a shadowed scope still rewrites. In a CHECK or a column DEFAULT / generated expression, a bare `new.` / `old.` qualifier names the row being written and survives renaming a table literally called `new` — a partial-index predicate has no written-row context, so `new.x` there is an ordinary reference and follows the rename. The same walk, run read-only, decides the assertion drop guard, so an assertion whose body merely declares a same-named CTE does not block `DROP TABLE` — the guard additionally follows view and materialized-view chains built on that walk, so an assertion reading a view over the table does block it (see [sql-ddl.md § 2.6.1](sql-ddl.md#261-createdrop-assertion-global-integrity-constraints)).

In a CHECK or column DEFAULT of a table that declares mutation-context variables, `context.<name>` naming one of them reads the variable, so it is not a reference to a table called `context` and does not follow its rename; renaming a table **to** `context` writes a self-qualified `t.<name>` naming a variable as `<schema>.context.<name>`, so it keeps reading the column. See [sql-ddl.md § 2.6.2](sql-ddl.md#262-mutation-context-table-level-parameters).

Whether a reference *is* a reference to the renamed object is decided by **resolving it the way the body's own planner would**, not by comparing bare names. An explicit `<schema>.<name>` means what it says; an unqualified name resolves against the body owner's home schema path (its own schema first, then the session `schema_path` — [`Database._homeSchemaPath`](../packages/quereus/src/core/database.ts)), against a snapshot of the catalog taken before the statement's first change. So with both `main.t` and `temp.t` present, a `main`-owned CHECK reading bare `t` follows `alter table main.t rename to t2` and is left alone by `alter table temp.t rename to t2`, while a `temp`-owned view reading bare `t` does the reverse — and either body's explicit `temp.t` follows only `temp.t`'s rename. Foreign keys are the one exception: an unqualified `referencedTable` always means the child table's own schema, never the session path.

Every dependent kind is walked across **every schema** — views, materialized views and assertions alongside tables (CHECK expressions, foreign keys, partial-index predicates, column DEFAULT / generated expressions). There is no own-schema limit: a view in `temp` over `main.t` follows `alter table main.t rename to t2`, and a `temp`-owned assertion naming `main.t` keeps enforcing. The resolution rule above is what keeps that from over-matching — a bare `t` in a `temp`-owned body is rewritten only when it resolves, under *that body's* home schema path, to the renamed object. So a bare `t` meaning `temp.t` is left alone by a rename of `main.t`, while a bare `t` in a `temp`-owned body that falls through to `main.t` (because `temp` holds no `t`) does follow it.

The rewrite also **preserves what each reference resolves to**: after rewriting, re-resolving the reference under the same home schema path — against the catalog as it stands after the rename — still yields the renamed table. When the bare new name would instead be captured by an *earlier* schema on the body's home path (with `temp.t2` present, `create view temp.v as select * from t` meaning `main.t`, then `alter table main.t rename to t2`), the propagation adds a schema qualifier — the body reads `main.t2`, not a re-bound bare `t2` — and it adds one **only** then, so the common no-collision rename leaves body text (and a materialized view's `bodyHash`) unqualified exactly as written.

That guarantee is not limited to the references the rename *rewrites*. A rename also **creates** a name, and the new name can capture a reference in a body that never mentions the renamed table at all: with `main.k` present and `temp` holding no `k`, `create view temp.v as select * from k` reads `main.k`, and `alter table temp.other rename to k` would otherwise silently re-bind it to the freshly created `temp.k`. Such a reference is schema-qualified too (the view reads `main.k`), and — again — only when the answer would actually change, so a body the rename cannot re-bind is left byte-identical and no unrelated materialized view's `bodyHash` churns. This arm covers the bodies that resolve unqualified names against the home schema path: view bodies, materialized-view bodies and assertion checks. A CHECK constraint, a column DEFAULT / generated expression and a partial-index predicate are not affected, because they plan under their owning schema alone (see the resolution rule above) — a bare name in one of them that resolved through to another schema could never be evaluated in the first place.

The same guarantee extends to a body's **qualifier namespace** — the names its `FROM` sources expose for use as column qualifiers. Renaming an unaliased source onto a name already visible as a qualifier where that source sits — a sibling source in the same `FROM`, a sibling's alias, a CTE declared in an enclosing `WITH`, a binding contributed by an enclosing `FROM` (a correlated subquery), or an inner alias deeper in the same select that would capture a correlated qualifier — pins the pre-rename spelling as an explicit alias: `select t.x, t2.x from t join u as t2 …` becomes `from t2 as t join u as t2 …` under `alter table t rename to t2`, and `t.x` keeps reading the renamed table instead of collapsing onto whichever same-spelled source wins. When the colliding name is a CTE, the source is schema-qualified as well (`from main.t2 as t`), since a bare source spelling a CTE's name would bind the CTE, not the table — the same applies to a DML target renamed onto a name its statement's own `WITH` declares. A source that already carries an author alias needs no pin (the alias is the qualifier, and a rename never moves it), and a rename with no collision adds no alias, so unaffected bodies stay byte-identical. The alias is pinned conservatively — whenever the new name is visible in scope or introducible inside the select, even if nothing in the source's subtree actually spells it — since a redundant alias is harmless while a missed one silently rebinds qualifiers. The declarative differ treats these engine-authored spellings (the pin qualifier and the pin alias) as the rename's own artifacts, not body edits, so `apply schema` converges in one pass and never recreates a pinned body back to its capturable spelling.

**Known limitation — `CREATE TABLE` and `DROP TABLE` shift what a bare name means in exactly the same way**, and neither has a propagation pass to correct dependent bodies: creating a `temp.k` re-binds a `temp`-owned body's bare `k` away from `main.k` just as the rename above would. Explicitly qualify a cross-schema reference to pin it.

A rename inside a transaction also follows any **deferred constraint check** the transaction has already parked (a `deferrable initially deferred` FK evaluates at `COMMIT`, against a plan compiled when the row was written). Each parked check records the renames that happened after it was queued and resolves its table reads through them, so the check still finds the table under its current name at commit — whether the renamed table is the one that owns the row or the one the check reads. The record is per parked check, so a **freed name reused by a fresh table** in the same transaction is not redirected: after `alter table pp rename to pp2; create table pp (...)`, a check parked before the rename still reads the original table (now `pp2`), while anything written afterwards reads the new `pp`.

## RENAME COLUMN

As with `RENAME TABLE`, references in CHECK expressions, FOREIGN KEY `referencedColumnNames`, partial-index `WHERE` predicates (unqualified and table-qualified refs on the renamed table, resolved against the indexed table the same way an implicit CHECK seed is; the derived UNIQUE constraint of a unique partial index shares the rewritten AST), view bodies, view/MV `with defaults` clauses (stored inside the body select; the clause's target names a base column of the view's FROM table — usually projected away — and rewrites via the same scope-aware synthetic-probe path a `with inverse` target uses, so a clause-only rewrite still fires the modified event; expr subqueries rewrite scope-aware — see [vu-inverses.md § View defaults](vu-inverses.md#view-defaults)), materialized-view bodies (a bare passthrough projection's exposed output name follows the rename, carried onto the backing table in place — see [mv-schema-change.md § Rename propagation](mv-schema-change.md#rename-propagation-mv--faster-view)), and assertion CHECK expressions (rewritten in place, violation query regenerated; same all-schema scope and same resolution rule as `RENAME TABLE` above) are propagated. Inside dependent SELECTs the rewrite follows scope: an unqualified column reference resolves when **any** FROM source in scope binds the renamed table (or a CTE that re-exposes the renamed column under the same name), aliased or not — an alias adds a qualifier, it does not take the source's columns out of scope, so a bare `x` written against `from t a` binds `t.x` exactly as it would against `from t`. A qualified reference resolves against the source's one qualifier: its alias when it carries one, its bare name otherwise — which is why `select t.x from t a` does not resolve here, matching the planner, and why an unqualified reference that legitimately binds some *other* source in the same FROM (`select 1 from u b where x < 0`, where `u` has an `x`) is left alone. A CTE re-exposes the renamed column when it has no explicit column list (`with c as ...` not `with c(x) as ...`) and at least one result column is a passthrough of the renamed column (an unaliased `select k`, `t.k`, or `select *` from the renamed table).

A CHECK expression may also name the renamed column through a **row-image qualifier** (`check (new.k > 0)`, `check on delete (old.k > 0)`), and that spelling is rewritten too. It follows scope like everything else here: `new` and `old` are ordinary identifiers in this parser, so a qualifier rebound by an inner FROM — a real table called `"new"`, a source aliased `"new"`, a `with "new" as (…)` clause — is left alone. The other direction holds as well: renaming a column of a table literally called `new` or `old` leaves **other** tables' row-image qualifiers untouched — a `check (new.v > 0)` on some other table names *that* table's written row, not the renamed table's column — and the same applies to their DEFAULT and generated expressions. A `with inverse` expression's `new.` references are likewise inert to rename propagation under **both** verbs — `RENAME COLUMN` and `RENAME TO` — since they name the enclosing select's output row rather than any table (see [sql-select.md § Result-column inverses](sql-select.md#result-column-inverses-with-inverse) and [vu-inverses.md § Authored inverses](vu-inverses.md#authored-inverses-with-inverse)).

The two expressions carried on a **column** are propagated on the same terms: a column `DEFAULT` reading a sibling through the row-image qualifier (`b integer default (new.a + 1)`, however authored — inline, or by `ALTER COLUMN … SET DEFAULT`, which writes the same catalog field), and a **generated column's** expression reading a sibling *bare* (`g integer generated always as (a + 1)`). Both resolve against the owning table the way a CHECK does, so the same walk decides all three and the scope rules above — case folding, the rebound-`new` edge — apply unchanged. A default or generated expression on *another* table reaches this one only through a subquery, where the reference resolves against that subquery's own FROM. Without this propagation the table stops accepting rows after the rename, since the default or generated expression no longer names a column that exists.

In a CHECK or DEFAULT of a table that declares mutation-context variables, a bare name or `context.<name>` that reads a variable is not a column reference: renaming a same-named column leaves it alone. Renaming a column **to** a declared variable's name is refused while a CHECK of the table reads that column bare, since the CHECK would then read the variable; qualify the reference as `<table>.<column>` or `new.<column>` first. See [sql-ddl.md § 2.6.2](sql-ddl.md#262-mutation-context-table-level-parameters).

The propagation is **transitive**. Rewriting a view or materialized-view body can shift the name that object *publishes* (`select id, x from t` starts publishing `y`), so the statement re-runs the whole propagation with that object as the rename target — breadth-first, until no published name shifts (`runtime/emit/column-rename-cascade.ts`). A second view over the first, an assertion over either, and a materialized view anywhere in the chain all follow (an MV's backing columns are renamed in place, so *its* readers follow in the next round). Two things stop the cascade at an object, because they pin its published names: an explicit **alias** (`select x as x from t` still publishes `x`; its readers are deliberately not rewritten) and an explicit **column list** (`create view v(a, b) as …` publishes `a, b` regardless of the body). A `select *` body cascades — its text never names the column, but what it publishes shifts with the source. `RENAME TABLE` needs no cascade: it changes no dependent's published names. If following the rename would make a dependent view or materialized view publish **two columns of the new name** (it already publishes `new_col` alongside a bare passthrough of the renamed column), the statement is refused up front — before any side effect — naming the dependent and the colliding column, mirroring the refusal of a rename that collides with an existing column on the table itself.

A partial index on the renamed table survives as a **live structure**, not just a catalog entry: the module rewrites the predicate as part of the rename, before rebuilding its index structures against the new column list. If the rewrite or the rebuild fails, the whole `RENAME COLUMN` fails and both the table and the stored predicate are left untouched — a rename never silently loses an index the catalog still advertises.

An **unnamed** `UNIQUE` constraint covering the renamed column has its covering structure renamed too. That structure's name is `_uc_<covered column names>`, derived from the columns' current names and recorded nowhere, so `rename column a to z` moves it from `_uc_a` to `_uc_z`; the structure stays hidden from `schema()` / `index_info()` under the new name and keeps enforcing, on both backends. The one visible consequence: the statement is **refused** with a `CONSTRAINT` error when the post-rename name is already held on that table — by an index, since accepting it would silently reclassify the user's index as a hidden backing structure, or by another UNIQUE constraint's covering structure, since the two constraints would then share one structure and the moved one would be enforced by a structure keyed on the *other* constraint's columns (see [SQL Virtual Tables § 6.3](sql-vtab.md#63-indexes-on-virtual-tables)). The refusal happens before the module is called, so the column keeps its old name and the other object is untouched — rename or drop it first, or name the constraint so its structure stops tracking the column. A **named** `UNIQUE` is unaffected: its structure takes the constraint's name.
